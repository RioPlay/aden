[[adr-004]]
= ADR-004: Append-Only AGENTS.md Guidance Block

[sidebar]
.What is an ADR?
****
Architecture Decision Records capture why a decision was made, not just what
was decided. No code should implement this decision before the ADR is accepted.
****

== Context

Aden only pays off when the AI agents working in a repository actually *use* it —
reaching for `grep`/`ask`/`asm`/`query` instead of raw text search, and trusting
the graph to be fresh rather than calling `gen` on every turn. That knowledge has
to live somewhere the agent harness loads automatically.

`aden init` already scaffolds a rich `.agent/` workspace, including
`.agent/templates/aden-guide.adoc` — a thorough "How to Use Aden Correctly"
reference. But nothing aden writes lands in the one file the major harnesses
(Claude Code, Cursor, Codex, OpenCode) auto-load: a root `AGENTS.md` (and its
common alias `CLAUDE.md`). So the guidance only reaches the agent if a human
hand-copies it. In practice that means most projects adopt aden and never tell
their agents how to use it.

The fix is for `aden init` to seed a short usage block into the root `AGENTS.md`.
The hazard is obvious: `AGENTS.md` is the *user's* file. An onboarding tool that
rewrites, reorders, or clobbers it is hostile, and teams will (rightly) stop
trusting `aden init`.

== Decision

`aden init` MAY write a single, clearly-marked guidance block into the repo-root
`AGENTS.md`, under strict guest rules. Aden owns only its own block; the user owns
the file.

. *Fenced, marked block.* Everything aden writes lives between sentinel markers:
+
[source]
----
<!-- BEGIN aden:guidance (managed by `aden init` — edit outside this block) -->
...short guidance...
<!-- END aden:guidance -->
----

. *Idempotent, never duplicated.* If both markers already exist, replace *only*
  the text between them (so re-running `init` or upgrading aden refreshes the
  snippet in place). If they do not exist, *append* the block to the end of the
  file. Never touch a single byte outside the markers.

. *Create only if absent.* No `AGENTS.md` at all → create one containing just the
  block. One already exists → append; never restructure the user's content.

. *One file, not two.* `AGENTS.md` and `CLAUDE.md` are frequently symlinked or
  `@import`-ed into each other. Aden maintains only `AGENTS.md` and, at most,
  mentions `CLAUDE.md` — it does not silently keep two files in sync.

. *Opt-in, visible, reversible.* The behavior is gated behind an explicit flag
  (`aden init --agents-md`). When it runs, it prints what it did and how to opt
  out ("remove the aden:guidance block"). Deleting the block fully removes aden
  from the file; a subsequent `init` without the flag will not re-add it.

. *Small surface.* The block is the minimum that changes agent behavior: the
  which-tool-when table, the `grep → asm/query → ask` flow, and the
  fresh-by-construction (auto-reindex) fact — then a pointer to
  `.agent/aden-guide.adoc` for depth. The less aden injects, the less it can
  step on.

== Consequences

* Projects that opt in get agents that use aden by default, with no hand-copying.
* The user retains full ownership: the block is labeled, self-contained, and
  removable in one stroke; everything outside it is untouched on every run.
* Because the default is opt-out (flag-gated), `aden init` never surprises a user
  by editing a file they consider theirs.
* `aden-guide.adoc` should also lead with the fresh-by-construction fact, so the
  short block and the deep reference agree.
