= ADR-010: Structural Remediation — Indexer Strangler, Advisory Policy, MCP Freshness

== Context

As of 2026-07-02, Aden is in good health: tests pass, `aden check --severity Forbid`
is green, and the product thesis (typed knowledge graph for agents) is sound. The
remaining debt is *structural concentration* and *documentation honesty gaps*:

* `crates/aden-cli/src/commands/generate.rs` (~2,770 LOC; `cmd_gen_inner` alone ~1,400
  LOC) concentrates the write/index pipeline in a single god module with ~185 downstream
  impact nodes.
* `aden-parse` and `aden-graph/src/parser.rs` duplicate parsing paths (unification
  deferred until after indexer extraction).
* `aden-policy::PolicyEngine` is only bootstrapped in `ci.rs`; `[constitution]` blocks
  are not fully enforced across `check`/`lint`/`diagnose`.
* MCP scoped `ADEN_SKIP_AUTO_GEN` to read tools only (Phase 2A shipped); write tools
  (`gen`, `ready`, `sync`) refresh without skip. Docs previously claimed unconditional
  "fresh by construction" without noting the MCP exception or stale-graph risk.

This ADR records the remediation strategy locked after gstack eng + DX reviews
(2026-07-02). See `AUDIT_REMEDIATION_PLAN.md` for the phased execution checklist.

== Decision

=== 1. Indexer extraction: strangler inside `aden-cli` first

The write path (`gen`, freshness checks, link/merge logic currently in `generate.rs`)
will be extracted incrementally into:

----
crates/aden-cli/src/indexer/
  mod.rs
  link.rs
  merge.rs
  fresh.rs
  gen.rs
----

**Rules:**

* **Never** target `aden-index` for this extraction — that crate is BM25/dense hybrid
  search (~3,200 LOC), not the compile/index pipeline.
* **PR-0 gate:** an equivalence test (`build_from_storage` vs `build_from_directory` on a
  fixture) must pass before any module move.
* A dedicated crate (`aden-compile`, name tentative) is deferred until the strangler
  module is stable for 2+ weeks.
* **High-care modules** (improvements welcome; require tests + blast-radius review):
  `aden-core/src/contract.rs`, `aden-store/src/fjall_store.rs`. No blanket freeze.

=== 2. Policy enforcement: advisory first

`[constitution]` and `[security]` directives (`Forbid`, `Warn`, `Suggest`, `Allow`) will
be surfaced in `diagnose`, `lint`, and `check --json` as `policy_violations[]` before any
hard blocking is enabled.

| Phase | Behavior |
|-------|----------|
| 0.2.x (current) | Advisory only — violations reported, CI/`gen` not blocked by policy engine |
| 0.3.0+ (future) | Optional `ADEN_POLICY_MODE=enforce` may block `gen`/`ci-check` after census |

`PolicyEngine::load_bootstrap` in `ci.rs` remains the only wired enforcement path until
Phase 3 lands. `aden check` reference integrity (orphan anchors, unresolved `<<ref>>`)
is independent of constitutional policy.

=== 3. MCP freshness model

The MCP server (`aden-mcp`) shells out to the `aden` binary. Two behaviors affect graph
freshness:

==== 3.1 Environment isolation

Every MCP invocation runs `env_clear()` and re-injects only `ADEN_*`, `PATH`, `HOME`,
`USER`, and `SHELL`. Host secrets (API keys, tokens) do not leak to child processes.
See <<security-model>> threat table.

==== 3.2 `ADEN_SKIP_AUTO_GEN`

MCP sets `ADEN_SKIP_AUTO_GEN=1` on **read-only** tool invocations only. Write tools
(`gen`, `sync`, `ready`, `heal --fix`, …) run without skip so they can refresh the store.
When set, read tools skip silent incremental `gen` in `ensure_fresh()` — avoiding
store-lock contention when the host may be running `aden ready` or another writer.

**Implications for agents:**

* First-time projects with no store still trigger an initial `gen` (store-missing path
  is not skipped).
* Existing stores may be stale relative to working-tree edits until an explicit `gen`,
  `sync`, or `ready` runs.
* Read-tool JSON envelopes include `index_stale` (and `stale_hint` when true) so agents
  can detect staleness without parsing human `NOTE:` lines.

Shell CLI usage (no `ADEN_SKIP_AUTO_GEN`) retains full auto-fresh behavior: read tools
reindex changed files on each invocation.

==== 3.3 Agent guidance

| Context | Freshness expectation |
|---------|----------------------|
| Shell `aden grep` / `ask` / … | Auto-reindex on read (default) |
| MCP read tools | May serve stale graph until explicit `gen`/`sync` |
| After large external change (clone, merge) | Run `aden gen` regardless of transport |

The magical workflow (`understand` → edit → `impact-diff`) must not regress during
remediation; blast-radius tools stay on the `essential` MCP surface.

== Consequences

**Positive:**

* Incremental refactor with PR-0 equivalence gate reduces regression risk on the highest-
  impact module (`generate.rs`).
* Advisory policy unblocks honest docs without premature `gen` blocking.
* MCP freshness docs prevent agents from assuming silent reindex over MCP.

**Negative / trade-offs:**

* Strangler inside `aden-cli` delays compile-time boundary enforcement until a future
  `aden-compile` crate.
* Advisory policy means `[Forbid]` directives are not yet hard gates outside `ci-check`
  bootstrap.
* MCP read tools may serve a stale graph until explicit `gen`/`sync` — agents must
  check `index_stale` in JSON envelopes or run write tools after substantive edits.
