= LG-103: Maintainer continuity and ownership

The packet remains `ready` while its linked GitHub delivery state remains
admissible. A closed issue retaining the `packet-blocked` label is an
administrative pause and leaves this packet resumable; a closed issue without
that label must be reopened or reconciled to a terminal packet state. Neither
tracker state blocks BDFL approval, merge, or release under the sole-maintainer
governance model documented here.

== Outcome

Aden has an explicit sole-maintainer governance model: the BDFL can accept,
review, release, and respond to security issues without an additional approval.
Continuity roles may be added later by consent, but are not a prerequisite for
operation or release.

== Current evidence

`MAINTAINERS.md` names RioPlay as BDFL and sole approval
authority. It records ownership, emergency authority, succession boundaries,
and the absence of any appointed backup responder.

== Scope

Maintainer, security, ownership, review, and contribution governance documents.

== Acceptance

* Crates and compatibility surfaces name the BDFL as accountable owner.
* Schema, migration, security, and release changes require documented BDFL
  approval and applicable validation, not another approval.
* Succession, inactivity, emergency authority, and decision appeal are defined.
* Any future backup responder or additional maintainer requires explicit consent
  and is advisory unless the BDFL later changes this policy.

== Non-goals

No foundation, trademark, funding, or multi-company governance structure.

== Failure modes and rollback

Paper ownership without willing people creates false confidence. Unfilled roles
remain visibly unappointed rather than naming contributors without consent, and
their absence does not limit the BDFL's authority to merge or release.

== Completion evidence

Role matrix, ownership map, documented BDFL approval process, and emergency
procedure.
