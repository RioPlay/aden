= AP-103: Authoritative freshness contract

== Outcome

Callers can prove which source revision a graph result represents and request an
authoritative answer that never silently serves lagging data.

== Current evidence

Reads can return `lagging` immediately after explicit generation, and freshness
uses cache presence plus whole-second modification times.

== Scope

Freshness policy, generation revisions, snapshot reads, MCP adaptation, and tests.

== Non-goals

No graph daemon or retrieval-ranking changes.

== Acceptance

* Existing `current`, `snapshot`, `lagging`, `building`, and `unavailable` states
  receive a compatibility-preserving migration contract.
* Results include graph revision, observed source fingerprint, and refresh cause.
* `--require-fresh` waits within a bound or fails actionably.
* Tests cover same-second edits, gen-immediate-read, rename/delete, writer timeout,
  failed gen, frozen mode, MCP root switching, multiple repos, and mid-query mutation.

== Failure modes and rollback

Failing authoritative reads is safer than false freshness. Preserve fail-open
exploration only when the receipt identifies the degradation.

== Completion evidence

Revision matrix, timeout/error fixtures, CLI/MCP parity, and updated documentation.
