[[security-model]]
= Security & Permissions Model

Aden embeds security as a first-class concern because it is designed for automated agents that read files and execute commands.

== Threat Model

Aden assumes the following threats:

|===
|Threat |Mitigation |Status

|Path traversal via `include::[]` |Canonicalize paths, reject anything outside project root |Implemented
|Binary planting via PowerShell discovery |Avoid cwd resolution |Implemented
|Hardcoded secrets in source |Secret scan in `ci-check` |Implemented
|Unsafe Rust code |Zero `unsafe` blocks in application/library code (test + MCP startup env hacks only) |Enforced
|Stale context leading to wrong decisions |`heal` detects drift, `check` validates integrity |Implemented
|Excessive token budget leaking context |Token budgeting with ~4-bytes-per-token heuristic, hard cap |Implemented
|Malicious contract injection |Store-first architecture (ADR-003): no contract files are written to the working tree; the graph store lives in the per-user data directory, not the repo. |Implemented
|Path args escaping the project root over MCP |`confine_path_args` rejects any path/out/from argument resolving outside the project dir |Implemented
|Argument injection via leading-dash values over MCP |`--` end-of-options terminator separates injected flags from user values in `build_cli_args` |Implemented
|Unbounded/blocking MCP tool execution |120s `COMMAND_TIMEOUT` bounds every spawned command |Implemented
|Host secret leakage via MCP child env |`env_clear()` + allowlist (`ADEN_*`, `PATH`, `HOME`, `USER`, `SHELL`) on every spawned `aden` |Implemented (<<adr-010>>)
|===

== Include Directive Security

Include directives (`include::path[]`) are bounded to the project root:

1. The path is canonicalized (no `..` traversal)
2. The resolved path must be under the project root
3. If the path resolves outside, the include is rejected with an error

This prevents an agent from accidentally (or maliciously) inlining `/etc/passwd` or other sensitive files.

== Secret Scanning

`aden ci-check` includes a secret scan that checks for:

- Hardcoded passwords (regex matching `password = "..."` assignments)
- API keys (AWS `AKIA...`, GitHub `ghp_`/`gho_`, OpenAI `sk-...` patterns)
- Long hex strings (possible API keys)
- Content hashes in the per-user cache dir (ADR-003) and generated files are excluded (false-positive suppression)

Any detected secret fails CI — the secret-scan gate returns an error on detection.

[NOTE]
====
The `gen`/index secret floor has **two layers**: (1)
`aden_core::filter::is_secret_path` blocks known credential files by filename,
extension, and parent directory; and (2)
`aden_core::filter::content_has_high_confidence_secret` scans file *content* and
refuses to index any file carrying a structured credential token (AWS, GitHub,
OpenAI, Slack keys, or a PEM private-key block) — so a key embedded in an
ordinary `config.json`/`settings.yaml` is kept out of the graph too. The content
screen is deliberately high-confidence (structured tokens only, no entropy
heuristic), so a credential in an unrecognized custom format could still slip
through; add such files to `.adenignore` to be sure. This two-layer gen secret
floor is applied at *indexing* time only; the read tools `grep`/`locate`/`audit`
operate on raw file content and are NOT redacted — don't assume their output is
secret-filtered.
====

== Permissions Model

The example below models principals, roles, and actions as a knowledge graph.
This illustrates modeling a permissions domain *in* Aden — Aden itself does not
implement an internal permissions/RBAC system:

[semantics]
----
Principal IsA Actor
Role IsA Principal
User IsA Principal
ServiceAccount IsA Principal
AdminRole IsA Role
EditorRole IsA Role
ViewerRole IsA Role
SuperAdmin IsA AdminRole
Permission IsA Entity
read_action IsA Permission
write_action IsA Permission
delete_action IsA Permission
AdminRole Invokes delete_action
AdminRole Invokes write_action
AdminRole Invokes read_action
EditorRole Invokes write_action
EditorRole Invokes read_action
ViewerRole Invokes read_action
SuperAdmin Invokes delete_action
----

== Constitutional Directives

The `[constitution]` block declares governance rules with precedence-ranked directives:

|===
|Directive |Behavior (0.3.x advisory mode)

|`Forbid` |Reported in `diagnose`/`lint`/`check --json`; Aden 0.4.0 does not enable policy-engine hard blocking by default
|`Warn` |Surfaces in output, CI passes
|`Suggest` |Non-blocking recommendation
|`Allow` |Explicitly permits an otherwise forbidden pattern
|===

Overrides require `:justification:` and `:reviewer:` attributes.

NOTE: As of 0.3.x, `PolicyEngine` enforcement is **advisory** outside `ci-check`
bootstrap (`PolicyEngine::load_bootstrap` when `.aden/constitution.adoc` exists).
`aden check` reference integrity (unresolved `<<ref>>`, orphans) is separate from
constitutional policy. Full wiring is tracked in <<adr-010>> Phase 3.

== Safe Execution

Aden takes several steps to ensure safe execution of agent commands:

1. **Id & Filename Sanitization** — Proposal IDs are validated against ASCII-safe whitelists before being used as filenames
2. **JSON Deserialization** — Bounded and uses `deny_unknown_fields` to prevent injection
3. **No `unsafe` Code** — The project contains zero `unsafe` blocks in application/library code (only test isolation and MCP startup env var hacks)
4. **PowerShell Discovery** — Avoids cwd resolution to prevent binary planting attacks
5. **Store overrides** — `$ADEN_STORE` / `$ADEN_DATA_DIR` are power-user escapes that bypass per-project keying and creation guards; use with care (see ADR-003)
