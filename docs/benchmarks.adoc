= Aden Benchmarks

These are early, self-run measurements on specific corpora.
They are not a standardized third-party benchmark.
All numbers are reproducible from `scripts/` and
`research/topics/aden-connection-audit/` (raw logs).

Every figure is tagged with its provenance:
`[measured]` — directly observed in a documented bench run;
`[estimated]` — derived via a stated model with explicit assumptions;
`[third-party]` — reported by an external publication, not an Aden measurement.

Lead claim: the data supports honest interest, not marketing copy.
If a number surprises you, check the methodology note attached to it.

== Token Efficiency [measured]

*Source:* `research/topics/aden-connection-audit/` bench run 2.
Eight developer questions on Aden's own repository (244 files).
Baseline: a grep-and-read agent that opens up to 5 full files per question.
Token count via `ceil(chars/4)` proxy — not a BPE tokenizer.
Failed-ask recovery costs are *included* on Aden's side (conservative).

|===
|Metric |Value

|Overall ratio (sum/sum) |*10.8×* (34,739 vs 374,028 tokens)
|Median per question |*134×* (range 3.8×–1,839×)
|Symbol-level questions (locate/understand) |131×–1,839×
|Conceptual `ask` questions |3.8×–5.2×
|vs whole-repo-in-context |~152× (4.3 k mean/query vs ~660 k source tokens)
|===

The distribution is bimodal.
Symbol and structure lookups (`locate`, `understand`, call-graph queries) show
the largest wins because Aden returns the specific subgraph rather than raw file
content.
Conceptual `ask` questions show smaller gains (3.8×–5.2×) — this is where
ask-routing can miss a relevant context cluster, driving extra round-trips.

*Caveats:*

* The chars/4 proxy undercounts both sides by roughly 10–30% for typical Rust/AsciiDoc
  source; the ratio is largely insensitive to this systematic bias because it
  affects numerator and denominator proportionally.
* Single mid-size repository workload; results on a much larger or smaller corpus
  may differ.

== Edge-Extraction Accuracy [measured]

*Source:* `research/topics/aden-connection-audit/` bench run 1.
A 79-edge hand-authored ground truth was written *before* running `gen` on a
purpose-built polyglot fixture (Rust / Python / TypeScript / Markdown / AsciiDoc).
Scored at commit `31719c7`.

|===
|Metric |Value

|micro-precision |*0.946* (70 TP / 4 FP)
|micro-recall |*0.886* (70 TP / 9 FN)
|micro-F1 |*0.915*
|===

7 of 11 edge types were perfect on this fixture.
Weakest edge types: `Supersedes` (P/R 0.50), `Calls` (P 0.778),
`Mentions` (P 0.857 / R 0.750).

*Caveats:*

* Single `gen` run; F1 is not averaged across runs.
* Small ground-truth set; edge-type breakdowns are noisy at this sample size.
* Scored against Aden's own edge vocabulary — a fixture crafted to exercise that
  vocabulary is a partial-credit check, not an independent benchmark.

== Retrieval Quality (BM25 vs Hybrid) [measured]

*Source:* `scripts/eval-sets/README.md`.
Deterministic build `9da0bcf` (5 fresh `gen` runs → byte-identical output).
Reproduce with `scripts/bench.py` and the query sets under `scripts/eval-sets/`.

=== Table 1 — Recorded 2026-06-07

|===
|Corpus |BM25 R@1 |Hybrid R@1 |BM25 R@5 |Hybrid R@5 |BM25 R@20 |Hybrid R@20

|create-t3-app cli/src (70 q) |0.229 |0.371 |0.429 |0.643 |0.614 |0.700
|Linux kernel subset, 4,114 .c (199 q) |0.362 |0.487 |0.472 |0.673 |0.608 |0.819
|===

=== Table 2 — M6 Five-Language Pilot (2026-06-09, validated after manual spot-check)

|===
|Repo |Lang |N |BM25 R@1 |Hybrid R@1 |BM25 R@20 |Hybrid R@20

|getkin/kin-openapi |Go |22 |0.273 |0.409 |0.455 |0.591
|rust-lang/rustfmt |Rust |21 |0.095 |0.095 |0.191 |0.238
|unoplatform/uno |C# |20 |0.150 |0.150 |0.150 |0.300
|pallets/flask |Python |17 |0.176 |0.176 |0.235 |0.294
|TanStack/query |TypeScript |11 |0.091 |0.182 |0.182 |0.364
|===

*Pattern:* hybrid retrieval beats BM25 on every corpus at every recall depth.
The gain is larger on larger corpora and at lower depths (R@1), where lexical
matching degrades fastest.

*Caveats:*

* Single-target ground truth (one expected file per query) is a lower bound on
  actual retrieval quality — any other relevant file is scored as a miss.
* Labels are self-authored from commit subjects mapped to files; spot-check pass
  rates 66–73%.
* Results on corpora with very different size or style (e.g. monorepo, heavy
  generated code) are not covered here.
* Not a standardized benchmark (BEIR, MTEB, etc.).

== Latency [measured]

*Source:* `research/topics/aden-connection-audit/` bench run 3.
Release binary, Aden's own repository (244 files, 2,592 contracts).
5 sequential runs, values are medians.

|===
|Command |Median latency

|`aden gen` cold |274 ms
|`aden gen` warm |308 ms
|`aden grep` |283 ms
|`aden locate` |278 ms
|`aden status` / backlinks / `asm` |~550 ms
|`aden ask` (symbol-anchored) |~1,571 ms
|`aden ask` (conceptual, escalation path) |48.2 s
|ripgrep (reference) |6.5 ms
|===

The ~250 ms floor on all store-backed commands is caused by `fjall` 2.11.2
`KeyspaceInner::drop`, which poll-sleeps ~250 ms per open/drop cycle waiting on
background threads (confirmed via gdb).
Every store-backed command pays 1–2 units of this cost.
The conceptual `ask` path opens and drops the store many more times during
escalation, which compounds to ~48 s.
A fast-path escape runs at ~9 ms, confirming ~10 ms is achievable once the
fjall drop is addressed.
The warm `gen` anomaly (308 ms > 274 ms cold) is a known side effect of the
no-op skip path; the difference is within measurement noise for this floor.

This latency issue is partially addressed: `--propose` now opens the store once
per run instead of per event (commit `be92d95`).

== Energy vs an LLM [estimated — NOT measured]

NOTE: No power draw was instrumented on either side of this comparison.
These figures are derived from a stated model with explicit assumptions.
Do not cite them as empirical measurements.

*Method:* measured token savings × published LLM inference energy estimates
(0.05–2.0 J/token; a 40× span from the literature) × an *assumed* CPU envelope
of 15–65 W (not measured on this hardware).

=== Per-question estimates

|===
|Side |Range

|Aden compute (1.91 s mean, assumed watts) |29–124 J/question
|LLM energy saved per question (conservative) |2,121 J
|LLM energy saved per question (aggressive) |84,822 J
|Aden compute as % of saved energy (worst case) |1.5–6%
|Aden compute as % of saved energy (best case) |< 0.1%
|Break-even J/token |~0.003 J (one order below any published estimate)
|===

=== At 1,000 queries/day

|===
|Scenario |Energy saved/yr |CO₂ at 400 g/kWh

|Conservative |~200 kWh |~81 kg
|Mid |~1,700 kWh |~685 kg
|Aggressive |~8,600 kWh |~3.4 t
|===

The 40× span in the J/token assumption propagates directly into a 40× span in the
conclusion.
Token savings correlate with, but do not equal, measured power savings: batching,
caching, and hardware efficiency curves at the provider side all shift the real
ratio in ways this estimate cannot capture.

*What a real comparison would need:*

. RAPL or wall-meter measurement of Aden CPU during a representative query set.
. Per-token energy figures from the LLM provider under matched batching and
  caching conditions (not published for most commercial APIs).
. Matched task-quality verification (same answer quality at same token budget).
. A mixed workload covering both symbol-lookup and open-ended question types,
  since the token ratio is bimodal.

== Third-Party Context [third-party]

The arXiv paper "Codebase-Memory" (2603.27277) reports approximately
10× fewer tokens, ~83% answer quality retention, and 2.1× fewer tool calls for
a comparable graph-context approach on developer question workloads.

This is cited as external corroboration that graph-based context compression is
a real phenomenon — it is *not* an Aden measurement, and the paper's methodology
and corpus differ from those described above.

== Cost Savings [estimated — derived from measured tokens]

Direct dollar conversion of the measured Token Efficiency run above
(34,739 vs 374,028 tokens over 8 questions → *339,289 tokens saved*, ~42,400 per
question). Prices are Anthropic's published per-token rates; the token base is the
`chars/4` proxy, so this inherits that proxy's bias.

The saved tokens are almost entirely *input* context — files a grep-and-read agent
loads that aden's subgraph omits — so they are priced at the *input* rate (the
conservative choice; displaced *output*/reasoning tokens cost 5× more and are not
yet captured here — that is the displacement bench, see <<planned-benchmarks>>).

|===
|Model (tier routed to) |Input $/1M |Saved $/question |Saved $/yr @ 1,000 q/day

|Claude Haiku 4.5 |1.00 |$0.042 |~$15,500
|Claude Sonnet 4.6 |3.00 |$0.127 |~$46,400
|Claude Opus 4.8 |5.00 |$0.212 |~$77,400
|Claude Fable 5 |10.00 |$0.424 |~$155,000
|===

*Caveats:*

* *Input-rate only.* Output tokens bill at 5× input; any displaced *reasoning* on
  the LLM side is undervalued here. The displacement bench will price both sides.
* *Prompt caching is the main downward force.* Repeated context bills at ~0.1× when
  cached, so a caching agent realizes less than the full-rate figure above; an
  uncached or cold-start agent realizes close to it.
* Inherits the `chars/4` proxy bias (~10–30% undercount) from the source run;
  the real-tokenizer correction (<<planned-benchmarks>>) retires it.
* Single mid-size repo, 8 questions — same scope caveat as the source run.

== Planned Benchmarks [planned]

These complement the measured suite above. They target the two weakest rows:
token savings (today only *compression* is measured, not *displacement*) and
energy (today entirely modeled). The detailed methodology spec is maintained
in the project's internal benchmark plan.

*Framing.* The existing token bench answers "aden gives the agent less to read."
These add the stronger axis: "aden does work the LLM would otherwise have to do at
all." When a deterministic command (`check`, `lint`, `impact-diff`, `understand`,
`heal`, `communities`) returns an answer, the work is done with *zero inference* —
tokens and GPU-joules that are never spent, not merely reduced.

=== Token savings

* *Displacement bench* — per deterministic command, tokens to *consume* aden's
  output vs tokens an LLM agent would burn to produce the same answer. Reported as
  a displacement ratio, separate from the compression ratio above.
* *Real-tokenizer correction* — re-run token benches through the model's actual
  tokenizer (`count_tokens`, not `tiktoken`), retiring the `chars/4` caveat.
* *Scaling curve* — run both ratios across the five eval corpora already in
  `scripts/bench.py` (Go/Rust/C#/Python/TS) to replace "single repo" with a trend.
* *Multi-turn trajectory* — end-to-end agent token spend with vs without aden in
  the loop, capturing the compounding fewer-tool-calls effect.

=== Power & cost savings

* *Measured aden energy (RAPL)* — `scripts/energy.py` reads CPU package + DRAM
  counters around each command (idle-subtracted, N≥20, medians), reported *with and
  without* the known fjall 250 ms floor. Moves aden's side of the energy story from
  `[estimated]` to `[measured]`.
* *Frontier-LLM comparison* — hosted inference can't be instrumented, so the LLM
  side stays modeled, but calibrated to the tier actually used and paired with a
  fully-grounded *cost* axis: dollars saved = displaced tokens × published
  per-token price (Opus 4.8 default, Fable 5 / Sonnet 4.6 / Haiku 4.5 as a
  sensitivity band). The joule axis stays `[estimated]` with an explicit
  prefill/decode split to narrow the current 40× span.

== Reproducing These Numbers

All benchmarks are reproducible from this repository:

[source,bash]
----
# Retrieval benchmarks (Tables 1 and 2 above)
scripts/bench.py
scripts/eval_corpus.py

# Query sets used in retrieval eval
scripts/eval-sets/

# Raw logs for token efficiency, edge accuracy, and latency
research/topics/aden-connection-audit/
----

The retrieval eval is deterministic: 5 fresh `gen` runs on the same source
produce byte-identical output (verified at commit `9da0bcf`).
