[[adr-002]]
= ADR-002: Secure Coding as a Built-in Aden Standard

[sidebar]
.What is an ADR?
****
Architecture Decision Records capture why a decision was made, not just what
was decided. No code should implement this decision before the ADR is accepted.
****

== Context

Aden ingests and reasons about untrusted code. Its own 2026-05-30 security audit
(see `<<adr-002-audit>>`) found nine confirmed defects whose root causes are
textbook secure-coding lapses — unbounded slicing, missing path confinement,
argument injection, information exposure. Every one mapped cleanly onto an
existing industry control (OWASP Secure Coding Practices) and weakness class
(MITRE CWE Top 25).

The maintainer's goal: make secure coding a *top-tier, built-in standard* for
aden — not a one-off `research/` corpus, but something aden ships and ideally
enforces. The proof-of-concept corpus in `research/secure-coding/` already
demonstrates aden can index this guidance and build a relationship graph across
weaknesses, mitigating practices, and aden's own findings.

The forces:

. We want secure-coding guidance *baked in* so every aden project inherits it.
. The richest external sources are copyleft/attribution-bound: OWASP material is
  **CC BY-SA**, MITRE CWE is under the **CWE Terms of Use**. aden's code is
  **AGPL-3.0**.
. CC BY-SA and AGPL are **not compatible for combination into one licensed
  work**. Embedding CC BY-SA prose into the AGPL binary (e.g. via
  `include_str!`) would create a license conflict.

== Decision

We will split "secure coding as a standard" into two cleanly-licensed layers:

. **Aden Secure-Coding Constitution (aden-authored, AGPL, embeddable).** A
  secure-coding policy written entirely in aden's own words — no copied
  copyleft text — covering the controls aden cares about for code-ingesting
  tools: validate/contain untrusted input at boundaries, never index outside a
  confined root, never slice untrusted bytes without a length guard, bound
  resource use (timeouts, size/recursion limits), treat data as data (argv not
  shell), don't leak host paths/secrets into output. Because it is original
  AGPL text, it MAY be `include_str!`'d into the binary and scaffolded by
  `aden init` as a `[constitution]` document. A subset is machine-checkable and
  can become `aden check` rules over time.

. **Reference Corpus (third-party, attributed, data-only scaffold).** The
  OWASP/CWE-derived documents (`research/secure-coding/`, CC BY-SA 3.0 + MITRE
  terms) ship as an *optional* scaffold — `aden init --with-secure-refs` writes
  them into the target project as separate, separately-licensed data files that
  aden parses. They are NEVER compiled into the AGPL binary. The aden-authored
  constitution `<<refs>>` these reference docs when present, giving the graph
  linkage without mixing licenses.

[[adr-002-audit]]
The constitution's content is informed by aden's own audit findings, which are
recorded (aden-authored) in `research/secure-coding/aden-audit-map.adoc`.

== Consequences

=== Positive
. Secure coding becomes a shipped default, not a one-off — `aden init` projects
  inherit aden's constitution.
. Zero license conflict: AGPL text in the binary, CC BY-SA/MITRE text only ever
  as separate attributed data files.
. A path to *enforcement*: a machine-checkable subset can graduate into
  `aden check` (aden already has `aden-policy` + a `[constitution]` concept).
. Dogfood: aden's own knowledge-graph features carry its security standard.

=== Negative
. Two artifacts to maintain (constitution + reference corpus) instead of one.
. The aden-authored constitution must be written carefully to NOT paraphrase
  OWASP text so closely that it becomes a derivative work (which would re-attach
  CC BY-SA). It must be genuinely original framing of the same engineering
  ideas (ideas/facts are not copyrightable; expression is).

=== Neutral / Risks
. Enforcement scope creep — keep the first `aden check` rule-set tiny and
  high-confidence (e.g. flag obviously-unbounded slices) to avoid false
  positives that erode trust.

== Licensing line (the load-bearing constraint)

[cols="1,1,1"]
|===
|Artifact |License |May embed in AGPL binary?

|Aden Secure-Coding Constitution (original) |AGPL-3.0 |YES (`include_str!` ok)
|OWASP-derived reference docs |CC BY-SA 3.0 |NO — data-file scaffold only
|MITRE CWE reference docs |CWE Terms of Use |NO — data-file scaffold only
|`aden-audit-map`, `index` (original) |aden-authored |YES if rewritten free of refs to copyleft docs
|===

== Alternatives Considered

[cols="1,2,1,1"]
|===
|Option |Pros |Cons |Rejected Because

|Embed OWASP/CWE text directly in the binary |One artifact; truly "hardcoded"
|CC BY-SA ⊗ AGPL license conflict |Illegal license mix
|Ship only as `research/` docs (status quo) |Simple |Not a built-in standard;
not inherited by projects |Doesn't meet the "built-in" goal
|Constitution + optional attributed scaffold (CHOSEN) |Built-in standard, no
license conflict, enforceable later |Two artifacts |—
|===
