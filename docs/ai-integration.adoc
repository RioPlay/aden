[[ai-integration]]
= AI Integration Guide: Keeping Agents in the Know

Aden was built for hybrid teams of humans and AI agents. This guide explains how AI agents should use `aden ask`, `aden asm`, `aden grep`, and `aden query` to stay synchronized with a codebase without reading every file.

== The Core Idea

An AI agent has a finite context window. A large codebase does not fit. Aden solves this by answering the question: "What is the smallest set of documents this agent needs to complete its task?"

The answer is assembled dynamically from the knowledge graph, not hard-coded in a prompt.

[[mcp-setup]]
== MCP Setup

Run Aden as a link:https://modelcontextprotocol.io[Model Context Protocol] server so an AI client (Amp, Claude, Cursor, Codex, Zed, Windsurf, opencode, …) queries your codebase graph directly — no copy-pasting CLI output.

`aden-mcp` is a *thin director*: it exposes Aden's CLI as MCP tools, each mapping 1:1 to an `aden` subcommand. There is no separate logic path — calling the `grep` tool runs the same code as `aden grep`, so everything documented for the CLI applies verbatim to the tools. The server operates on the target project you point it at; nothing it returns is specific to Aden's own source.

=== Prerequisites

The MCP server is a separate binary, `aden-mcp`. The repo's `./install.sh` builds and installs *both* `aden` and `aden-mcp` to `~/.local/bin`:

[source,bash]
----
./install.sh
aden --version
aden-mcp --version
----

NOTE: `cargo install --path crates/aden-cli` installs only the `aden` CLI and *omits* `aden-mcp`. Use `./install.sh` (or build `crates/aden-mcp` explicitly) for the MCP server.

=== Install into a client

[source,bash]
----
aden mcp install --platform <platform>
----

Supported `<platform>` values: `amp`, `opencode`, `claude`, `cursor`, `codex`, `zed`, `windsurf`.

Useful flags:

* `--project <PATH>` — select the project whose local client configuration is changed during installation. It does not pin that path into the server command; at runtime `aden-mcp` follows the client's MCP Roots/workspace environment.
* `--binary <PATH>` — point at a specific `aden-mcp` binary if it is not on `PATH`.
* `--scope <SCOPE>` — `user` (global) or `project` (local). Default: one user-global server for every platform; at runtime it follows MCP Roots/the host workspace, so it works across folders without per-project installation.
* `--preset <PRESET>` — workflow preset: `explore`, `verify`, or `admin`. Sets the default config name and tool surface.
* `--name <NAME>` — config entry name (default: `aden`). Use this to keep multiple local MCP profiles side by side.
* `--surface <LEVEL>` — override the preset/default tool surface: `essential`, `standard`, or `full`.
* `--dry-run` — print what would be written without touching any config.
* `--all` — install for every supported platform, not just detected ones.

IMPORTANT: Amp's default `user` scope writes `amp.mcpServers` to the global Amp settings file, which avoids workspace MCP approval. A project-scoped Amp entry in `.amp/settings.json` may require approval in Amp. Amp also accepts JSONC settings; Aden targets the plain `.json` settings path because its existing config merger does not preserve comments.

IMPORTANT: Claude Code's default `user` scope registers one global server named
`aden`; it is not a separate per-folder install. If you want each repository to
have its own Aden MCP server, run `aden mcp install --platform claude --scope
project` inside each repository (or pass `--project <PATH>` explicitly).

For token-controlled setups, install separate workflow presets instead of one
oversized tool surface. These are global by default and work in every workspace:

[source,bash]
----
aden mcp install --platform codex --preset explore
aden mcp install --platform codex --preset verify
----

`explore` maps to the essential navigation surface (`aden-explore`), `verify`
maps to the standard validation surface (`aden-verify`), and `admin` maps to the
full operational surface (`aden-admin`). Use `full`/`admin` only for setup/admin
sessions; it lists more tools and gives the
model more irrelevant choices during normal planning or implementation work.

Related: `aden mcp list [--preset <PRESET>|--name <NAME>]` (platforms + install status), `aden mcp uninstall --platform <platform>`, `aden mcp serve` (HTTP endpoint for CI/agent integration).

NOTE: Installation is currently explicit and non-interactive. Aden does not silently edit client configuration on first launch. Run `aden mcp install --dry-run` to inspect the proposed changes before opting in. A future first-launch prompt should preserve that consent boundary.

=== Verify it works

1. Confirm the binary is reachable: `aden-mcp --version`.
2. Check the client config was written: `aden mcp list`.
3. *Fully restart your AI client* so it loads the new server.
4. In the client, confirm the `aden` tools appear (e.g. `grep`, `ask`, `asm`, `query`, `locate`). Ask it to `grep` a known string and confirm matches come back tagged with their enclosing symbol.

If the tools do not appear, see <<troubleshooting>>.

`aden-mcp --version` is an installation smoke test: it prints the version and
exits without opening the JSON-RPC stdio transport. If it instead reports an
initialization/connection error, reinstall a current Aden release before adding
the server to a client configuration.

=== Argument conventions

* *Use `snake_case` argument names* (`dry_run`, `caller_of`, `show_context`). The server translates them to the CLI's `--kebab-case` flags.
* *Unknown arguments are rejected* at the schema boundary — a typo like `dept` for `depth` fails fast.
* *Booleans must be real JSON booleans* (`true`/`false`), not strings.
* *`locate` requires at least one of `symbol` or `caller_of`*.
* *Natural names or anchors.* `asm` and every `query` mode accept a unique symbol name, a module alias such as `mod-<crate>`, or a full `aden://…` anchor. Exact anchors and aliases win; equally ranked names return deterministic candidates instead of guessing. Use `locate` when a name is common or ambiguous. Substring/fuzzy matches are suggestions only and are never silently selected.

=== Tool choice and correctness limits

The MCP registry orders compact orientation and deterministic discovery before
heuristic routing: `tree --symbols` → `grep` → `locate` → `understand` →
`ask` → `query` → `asm`.

* `grep` is the default exact-content discovery tool. For architecture,
  performance, security, or completeness audits, use multiple materially
  different patterns and verify against targeted source reads.
* `locate` resolves canonical definitions and reports whether it fell back to
  full text. Use it before `understand` for short or common names.
* `understand` is strongest for a known canonical symbol. Nested/local/test
  symbols, generated code, macros, and dynamic calls may not be represented;
  no graph result does not prove absence.
* `ask` heuristically chooses one primary anchor for one bounded question.
  Recognizable repository-wide audits, exhaustive lists, rankings, and
  remaining-work questions return `needs_narrowing` without context. This guard
  catches common unsafe shapes, not every possible wording: inspect
  `question_fit`, `routing_confidence`, and the selected anchor. Corroborate
  consequential claims with `grep` and source evidence.
* `asm` context is a bounded graph neighborhood, not a complete source file.
  Read the located source range before making subtle edits.
* Aden does not replace Git history/status, filesystem inventory or metadata,
  compilation, tests, or source editing. Use the host tools for those jobs.
* Treat `freshness`, `index_stale`, `truncated`, and incomplete receipts as
  correctness signals, not optional metadata.

=== Transport-parity examples

These CLI calls exercise the same structured read contracts used by the MCP
`grep` and `locate` tools. They are run as documentation fixtures in CI:

[source,bash]
----
aden grep --json "known_symbol" .
aden locate --json --symbol "known_symbol" .
----

Over MCP, pass the corresponding named JSON arguments `pattern`, `symbol`, and
optional `path`. The response retains the CLI JSON semantics, including the
versioned `context_receipt`; text-first `ask` and `asm` responses are carried
losslessly in a versioned JSON envelope. Non-strict MCP responses also include
an `execution` receipt with selected root, scope-selection source, elapsed time,
deadline, and subprocess status. Strict `ask`/`asm` omit this optional metadata
so observability can never displace evidence from the caller's hard budget.

The omitted `path` defaults to the workspace supplied by the MCP client. For
repository-bound read operations in a multi-repository workspace—including
`ask`, `grep`, `locate`, graph traversal, and verification—Aden selects a
repository only when there is one candidate or the request contains one exact,
unique repository name. Otherwise it fails quickly with bounded candidate paths
and asks the caller to retry with `path`; it never silently chooses root zero or
launches a broad query and waits for a timeout. An explicit `path` always wins and may select any
of the client's declared MCP roots. Prefer `grep` for exact content discovery
and `ask` for a bounded semantic question.
Aden intentionally does not replace filesystem metadata or version-control
operations such as listing files by modification time or reading `git log`; use
the host's filesystem and Git tools for those operations.

=== Agent response contract

MCP capability schemas declare `x-aden-output-mode`. Read tools use
`json-receipt-v1`: every successful response is JSON and includes a
`context_receipt`. When a legacy CLI read has no native receipt, MCP returns a
truthful `freshness: "unavailable"` receipt and `incomplete: true`; agents must
not treat it as authoritative. MCP errors are JSON too, with a sanitized
message, `safe_to_retry`, and an exact `recovery` action. Symbol-resolution
failures add typed `ambiguous_symbol`/`anchor_not_found` codes and structured
`error.candidates`/`error.suggestions`; MCP requests this machine envelope from
the CLI directly rather than scraping human error lines. This removes any need
to parse terminal chrome to decide how to proceed.

=== Security boundary

* *Path confinement.* Tools operate inside the served project directory; the `path`/`--project` argument defaults to it and the server does not reach outside (including `heal`'s watch target).
* *Error sanitization.* CLI errors are scrubbed of panic backtraces and absolute paths, and capped in length.
* *Timeout.* Tool calls use cost-class deadlines: 30 seconds for cheap discovery,
  60 seconds for graph traversal, and 120 seconds for verification/build paths.
* *Concurrency.* Identical read calls for the same resolved project and
  arguments are single-flight: they share one CLI child and its bounded result.
  Distinct work admits at most two CLI children; batch independent requests in
  groups of two or fewer. Additional distinct calls fail fast with a retryable
  `server_busy` response instead of queueing behind a slow graph build. The
  response includes the `concurrency_limit`; retry only the rejected call after
  an active call completes.
* *`watch` is terminal-only.* The continuous file-watch / live-reindex mode is not exposed over MCP — run `aden watch` in a terminal; use `gen`/`sync` for one-shot updates.

[[mcp-freshness]]
=== Graph freshness (shell and MCP)

Shell CLI and MCP share one freshness contract. See <<adr-010>> for historical
context; the zero-friction model supersedes the old MCP skip-auto-gen default.

==== Shared behavior

Read tools (`grep`, `ask`, `locate`, `asm`, `query`, `search`, `understand`) call
`ensure_fresh()` before serving results. When the working tree has changed (edits,
new files, **deletes/renames**), a silent incremental reindex runs — you do **not**
need `gen` after every edit. Silent gen is **single-flight** and **non-blocking** on
the read path: if another writer holds `store.lock`, explore tools serve the last
`graph.snapshot` instead of waiting. Decision tools (`understand`, `impact-diff`)
wait briefly (a few seconds) for an in-flight refresh.

| Situation | What happens |
|-----------|--------------|
| No store yet (first query) | Initial `gen` runs — tools work out of the box |
| Store exists, files changed/deleted | Silent incremental gen (or join in-flight writer) |
| Writer busy during explore read | Answer from last snapshot; JSON `freshness` / `index_stale` |
| Blast-radius tool during writer | Short wait, then answer; may label `freshness: lagging` |
| Large external change (clone, merge) | Run `gen` regardless of transport |
| Escape hatch | Host may set `ADEN_SKIP_AUTO_GEN=1` to freeze the index |

JSON envelopes include `freshness` (`current` \| `snapshot` \| `lagging` \| `building` \|
`unavailable`) and legacy `index_stale` for older prompts. The versioned
`context_receipt` additionally identifies the `graph_revision`, the
`observed_source_fingerprint`, and the `refresh_cause`. The source fingerprint
is content-addressed (path plus bytes), so same-second and equal-sized edits do
not inherit the old whole-second mtime blind spot.

For an answer that must never silently use a lagging snapshot, pass
`--require-fresh` to a graph read, for example:

[source,bash]
----
aden --require-fresh query --impact aden://module/example#symbol . --json
----

The option is also exposed as `require_fresh: true` on the corresponding MCP
tools. Aden applies one five-second wall-clock deadline across source checking,
generation attempts, writer waits, and retries, then exits with status 2 and an
actionable error if authority cannot be proven.
Frozen mode (`ADEN_SKIP_AUTO_GEN=1`) therefore remains useful for offline
snapshot exploration, but intentionally fails an authoritative read after an
edit. Existing qualitative freshness labels remain unchanged during this
additive receipt migration.

==== Workspace auto-detect (MCP)

`aden-mcp` does **not** require a baked project path in client config. It resolves
the open workspace from MCP Roots (`roots/list`, `roots/list_changed`) and common
host env vars (`WORKSPACE_FOLDER_PATHS`, …). Optional pin: pass a path argument or
set `ADEN_PROJECT`. Re-run `aden mcp install` to drop legacy absolute paths from
older installs.

==== Concurrent reads within one project (ADR-011)

After each successful `gen`, aden publishes `graph.snapshot` beside the per-user store.
Read commands prefer that snapshot (even if the live store is briefly newer under a
concurrent writer), then fold in-tree overlays in memory. Explicit `gen`/`ready`/`sync`
still open fjall under `store.lock` (single-flight; second explicit writer waits).

| Situation | What happens |
|-----------|--------------|
| N concurrent read tools, no writer | Each loads `graph.snapshot` — no fjall open |
| `gen` running while reads are active | Reads use the last published snapshot |
| Snapshot missing | Fall back to opening fjall |
| Silent gen while lock held | Fail-open (no multi-minute queue) |

`aden status` (and `--json`) reports the active store writer and read-snapshot path.
See <<adr-011>> for format and publish rules.

== How `aden ask` Works

`aden ask` is an opt-in convenience interface for bounded, exploratory context
retrieval. It is not a chatbot wrapper around an LLM. It uses heuristic search,
anchor selection, and intent routing, so it is not authoritative discovery and
must not be treated as proof of repository-wide coverage.

Invocation:

[source,bash]
----
aden ask "How does the authentication flow work?"
----

What happens internally:

0. **Scope guard**: Unless `--from` pins a known anchor, recognizable
   repository-wide audits, exhaustive lists, rankings, and remaining-work
   questions stop immediately with `result_state: "needs_narrowing"`, an empty
   context, and recovery actions. This avoids indexing and spending context
   tokens merely to produce a misleading local answer. The deterministic guard
   covers common unsafe wording; callers must still inspect `question_fit` and
   `routing_confidence`.
1. **Search**: The question is tokenized and searched against the in-memory inverted index built from all `.adoc` / `.aden` contracts. Ranking is BM25 by default; when built with the `dense` cargo feature (and the local embedding model is present), it becomes hybrid — BM25 plus offline, deterministic local dense embeddings fused via Reciprocal Rank Fusion (RRF).
2. **Anchor resolution**: The top-ranked document anchor becomes the starting node (or you pin it with `--from`).
3. **Intent classification**: The question is classified into one of nine intents (the per-intent code edges below; every intent additionally traverses the semantic edges IsA, RelatesTo, SimilarTo, AssociatedWith, Explains, and `Calls` is always included):
   - `Debug` --- "Why does X fail?" → depth 3, edges: Constrains, Documents, Calls, Invokes, Requires
   - `Usage` --- "How do I use X?" → depth 2, edges: Uses, Invokes, Requires, Documents
   - `Explain` --- "What does X do?" → depth 2, edges: Uses, Calls, Implements, Documents
   - `Refactor` --- "Refactor X" → depth 4, edges: Calls, Uses, Mutates, Supersedes, Amends
   - `Impact` --- "What depends on X?" → depth 3, edges: Uses, Calls, Constrains
   - `List` --- "list/show me all X" → depth 2, edges: Uses, Documents
   - `Compare` --- "compare X and Y" → depth 3, edges: Uses, Documents, Constrains
   - `Count` --- "how many X" → depth 1, edges: Documents, Uses
   - `General` --- fallback → depth 2, edges: Uses, Documents, Constrains
4. **Graph traversal**: A BFS walk collects neighbors along the selected edge types, stopping at `max_depth`. Each node's neighbors are expanded in deterministic edge-priority order (most load-bearing types such as `Calls` first), so the budget favors the most relevant context and the output is reproducible.
5. **Token budgeting**: Each collected document is estimated with a bytes/4 heuristic; documents are included until the cumulative total (inter-document separators counted) would exceed the budget, and an overflowing final document is truncated at a word boundary. `asm` and normal `ask` context stay within their declared budgets. `ask --expand` explicitly opts into relevance-based growth (up to ~4x, capped at 32k); `ask --strict` caps the complete serialized response including receipts.
6. **Assembly**: Documents are concatenated with `\n\n---\n\n` separators. Output is stripped of AsciiDoc markup (anchors, refs, attribute lines, block delimiters) so every token carries signal.

== What to Do with the Output

Feed it directly into an LLM prompt. No preprocessing needed — the output is already token-dense:

[source]
----
You are an expert software engineering assistant.
The following context was retrieved from a knowledge graph.
Answer based ONLY on the provided context.
If the context does not contain enough information, say so explicitly.

---

[context from aden ask goes here]
----

This grounds the agent in real source structure, but it does not prove that the
selected neighborhood is complete. Inspect the selected anchor and receipt, and
use deterministic discovery for consequential claims.

=== Good and Bad `ask` Questions

|===
|Use `ask` for |Do not rely on `ask` for

|A bounded orientation question with a likely primary symbol: “What does
`assemble` do?”
|Exhaustive or negative claims: “Find every authentication path” or “Does this
repository contain no unsafe code?”

|A conceptual explanation after confirming the symbol with `grep` or `locate`.
|A decision that depends on all call sites, dependencies, tests, files, or
security-relevant occurrences.

|A first-pass context bundle that you will verify from its selected anchor.
|Ambiguous multi-concept questions such as “How does the whole system work?”
or questions whose answer must be reproducible without routing heuristics.
|===

The right-column shapes normally return `needs_narrowing` with no assembled
context. Do not evade that result by paraphrasing until the heuristic accepts
it; decompose the task into independent `grep`/`locate` evidence or pin a known
anchor when one neighborhood is genuinely sufficient.

For a consequential question, start with exact `grep` or `locate`, resolve the
canonical anchor, inspect `query`/backlinks or impact as needed, then use `asm`
for a controlled context bundle. Pin `ask --from <anchor> --strict` only when
its convenience is useful after that deterministic discovery.

== When to Use `aden asm` Instead

`aden ask` is opinionated: it classifies intent and picks edges automatically. `aden asm` gives you full control.

Use `aden asm` when you already know the starting anchor and want exact edge types:

[source,bash]
----
aden asm --from mod-aden-graph --depth 3 --budget 8192 --edge-types "Uses,Calls"
----

This is useful for:
- Custom agent pipelines
- Debugging why `aden ask` returned too much or too little context
- Building reproducible prompts for regression tasks

== When to Use `aden query`

`aden query --from <anchor> --depth N` traverses the graph and emits JSON —
ideal both for sanity-checking structure before asking and for programmatic
consumption:

[source,bash]
----
# Reachable nodes from an anchor
aden query --from mod-aden-core --depth 2 . | jq '.[] | .anchor'

# Everything that references this anchor (backlinks)
aden query --backlinks mod-aden-core . | jq '.[] | .anchor'

# Transitive closure over dependency edges (blast radius)
aden query --impact mod-aden-core . | jq '.[] | .anchor'
----

== Finding Symbols with `aden locate` and `aden search`

`aden locate --symbol <name>` finds symbol definitions (functions, types, modules). Falls back to full-text search if graph search finds nothing.

[source,bash]
----
# Find a function definition
aden locate --symbol assemble .

# Find with limit
aden locate --symbol "Error" . --limit 5
----

`aden search <query>` performs full-text search across all contracts:

[source,bash]
----
aden search "authentication" . --limit 10
----

== Getting Command Help with `aden suggest`

Not sure which command to use? Ask `aden suggest`:

[source,bash]
----
aden suggest "find all tests in the project"
# Suggests: aden search "test" or aden locate "test"
----

== MCP Tools (for AI Platforms)

When using Aden via MCP (OpenCode, Claude Code, Cursor, etc.), the server exposes
its CLI as tools — one per `aden` subcommand. The surface is *tiered* so the
default tool list stays focused on the navigation loop:

* *Essential* (default) — the find→comprehend→blast-radius loop. The smallest
  set that delivers aden's core value.
* *Standard* (`ADEN_MCP_SURFACE=standard`) — adds change-safety, verify, and
  orientation tools on top of Essential.
* *Full* (`ADEN_MCP_SURFACE=full`) — all tools, including setup/admin commands.
  The legacy `ADEN_MCP_FULL=1` env var is an alias for this level.

Tiering is both discovery and execution policy: a hidden Standard/Full tool is
rejected until that surface is explicitly enabled. Set `ADEN_MCP_SURFACE` in the
server environment (or bake it in at install time with `aden mcp install
--surface <level>`).

== Keeping the Graph Fresh

Stale context is worse than no context. Use this order in your agent loop:

1. Before starting work: `aden status .` (quick health check) or `aden check .` (validate integrity)
2. After writing code: `aden gen <path>` (index changed source)
3. Before committing: `aden ready .` (fast aden-only gates: gen + lint + check + heal drift + audit)
4. Before pushing to remote: `aden ci-check .` (full gate suite including external tools)
5. After large merges or file deletions: `aden sync .` (reconcile store — runs gen + check + heal with gc)

NOTE: Do NOT chain `aden gen` before `aden ready` or `aden ci-check` — both already run gen internally as their first step. Running gen twice wastes time and may produce inconsistent results.

If you are running as a persistent agent, use `aden watch` to auto-regenerate contracts on file changes.

== Understanding Drift Types

When `aden heal` runs, it detects these drift event types:

|===
|Drift Kind|Meaning|Auto-fixed by `--fix`?
|StaleHash|Source changed, contract hash stale|Legacy on-disk only (0.99); a store-resident StaleHash is skipped with a "run `aden gen`" hint
|SignatureMismatch|Symbol signature changed|Yes (0.90) — rewrites the signature in the store, not an on-disk stub
|MissingContract|Source symbol has no contract|Advisory: proposal points at the source and emits `aden gen <src> --auto .`; it does NOT materialize a stub (a stub has no `source_hash` and would self-drift as StaleHash)
|StaleMarkdown|Markdown's source files changed|Yes (0.80)
|MarkdownDrift|Markdown content drifted|No (confidence 0.75, below the 0.8 auto-fix threshold) — detect-only
|OrphanAnchor|Contract/anchor with no live source (deleted OR newly `.adenignore`-excluded)|No via `--fix`; removed via `--gc`
|BrokenReference|`<<anchor>>` points at a missing target|No (detect-only)
|DeadLink|`include::` path doesn't resolve|No (detect-only)
|MissingMarkdownTemplate|Markdown lacks its template|No (detect-only)
|===

NOTE: `--fix` only applies fixes with confidence ≥ 0.8.

NOTE: deleting a symbol or file no longer needs a manual step — `gen` prunes
removed symbols on re-index, and `aden heal . --gc` sweeps the store for
contracts whose source no longer exists.

Use `aden heal . --fix` for auto-fixing high-confidence issues.

== Token Economy Rules

Aden is designed with token scarcity in mind. Follow these rules:

- **Prefer bounded retrieval over dumping the whole repo.** Start with `grep` or
  `locate`; use `ask` only for a bounded exploratory bundle, or use `asm` when
  you need reproducible traversal.
- **Use `--from` to avoid search ambiguity.** One good anchor is worth ten vague keywords.
- **Lower `--budget` for focused tasks.** 2048 tokens is enough for most refactor questions.
- **Inspect machine signals before context.** Stop on `needs_narrowing`; treat
  `routing_confidence: "ambiguous"`, stale receipts, and truncation as reasons to
  refine discovery rather than consuming more context.

== Security Notes for Agents

- Aden assumes contracts are build artifacts. Never commit `.aden/`.
- Built-in exclusions skip common secrets, dependencies, and build output without
  a project file. `aden init --templates` adds a customizable `.adenignore` only
  when that larger project footprint is explicitly wanted.
- Include directives are bounded to the project root. Path traversal outside the repo is rejected at parse time.

== Compact LLM System Prompt

The MCP schemas already describe arguments. Do not duplicate the full command
catalog in every model turn. This compact policy is sufficient:

[source]
----
Use Aden for bounded code navigation.

1. Use tree(symbols=true) once for a compact codebase map, then grep for
   independent evidence; locate ambiguous symbol names.
2. Use understand for a known symbol, query for backlinks/impact, and asm for a
   bounded context bundle around a resolved anchor.
3. Use ask only for one bounded question about a named symbol, file, subsystem,
   or relationship. Stop and decompose the task when result_state is
   needs_narrowing. Treat ambiguous routing, stale receipts, and truncation as
   incomplete evidence.
4. Never infer repository-wide completeness or absence from one graph result.
   Verify consequential claims with distinct searches, targeted source reads,
   tests, builds, and Git/filesystem tools as appropriate.
5. Cite returned anchors. Omit tuning arguments and budgets unless the default
   bounded response is demonstrably insufficient.
----

Read responses are JSON with context receipts by default. Request human/LLM
prose only for direct display. Raw AsciiDoc remains available explicitly:

[source]
----
aden asm --from mod-aden-core --format aden .
----

== Common Patterns

=== Pattern 1: Understanding a New Codebase

[source]
----
1. grep(pattern="entry point|main")
2. locate(symbol="main")
3. understand(symbol="main")
4. ask(question="How does startup reach request handling?", from=<main-anchor>)
----

=== Pattern 2: Finding How Something Works

[source]
----
1. grep(pattern="authenticate")  # Independent content evidence
2. locate(symbol="authenticate") # Resolve the canonical anchor
3. asm(from=<auth-anchor>)         # Bounded context with defaults
----

=== Pattern 3: Making Changes Safely

[source]
----
1. locate(symbol="function_to_change")
2. query(impact=<resolved-anchor>) # See downstream risk
3. Read the returned source ranges and make the edit
4. Run project tests/build plus the configured Aden gate
----

== Anti-Patterns

- **Don't** call `asm()` with depth=5 (wastes tokens)
- **Do** start with depth=2, go deeper if needed

- **Don't** use vague questions like "tell me about the code"
- **Do** ask specific questions like "what is the entry point?"

- **Don't** ignore citations in aden output
- **Do** reference specific documents in your answers

- **Don't** assume aden knows everything
- **Do** use `check()` to validate, `heal()` to find gaps

== Troubleshooting

=== `aden ask` returns `needs_narrowing`

Do not paraphrase until the guard stops firing. Split the request into distinct
`grep` evidence queries, resolve each hit with `locate`, and use `query` or
`asm` on the resulting anchors. If the question genuinely concerns one known
neighborhood, pin that anchor with `from`.

=== `aden ask` returns "No relevant documents found"

Try specific identifiers from the source. Run `aden grep <pattern>` to discover
enclosing symbols and then resolve them with `locate`.

=== Output is too short

The graph parser currently stores document body content as raw text. If blocks are empty, it falls back to `raw_content`. If you see only titles, verify the `.adoc` files contain actual prose below the title.

=== DuplicateAnchor errors after `aden init`

Template files and instantiated files sometimes share anchors. Rename the instantiated file anchors (e.g., `[[agent-context]]` instead of `[[agent-context-template]]`) or delete the template files if they are not needed.
