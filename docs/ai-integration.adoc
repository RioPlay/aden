= AI Integration Guide: Keeping Agents in the Know

Aden was built for hybrid teams of humans and AI agents. This guide explains how AI agents should use `aden ask`, `aden asm`, `aden grep`, and `aden query` to stay synchronized with a codebase without reading every file.

== The Core Idea

An AI agent has a finite context window. A large codebase does not fit. Aden solves this by answering the question: "What is the smallest set of documents this agent needs to complete its task?"

The answer is assembled dynamically from the knowledge graph, not hard-coded in a prompt.

[[mcp-setup]]
== MCP Setup

Run Aden as a link:https://modelcontextprotocol.io[Model Context Protocol] server so an AI client (Claude, Cursor, Codex, Zed, Windsurf, opencode, …) queries your codebase graph directly — no copy-pasting CLI output.

`aden-mcp` is a *thin director*: it exposes Aden's CLI as MCP tools, each mapping 1:1 to an `aden` subcommand. There is no separate logic path — calling the `grep` tool runs the same code as `aden grep`, so everything documented for the CLI applies verbatim to the tools. The server operates on the target project you point it at; nothing it returns is specific to Aden's own source.

=== Prerequisites

The MCP server is a separate binary, `aden-mcp`. The repo's `./install.sh` builds and installs *both* `aden` and `aden-mcp` to `~/.local/bin`:

[source,bash]
----
./install.sh
aden --version
aden-mcp --version
----

NOTE: `cargo install --path crates/aden-cli` installs only the `aden` CLI and *omits* `aden-mcp`. Use `./install.sh` (or build `crates/aden-mcp` explicitly) for the MCP server.

=== Install into a client

[source,bash]
----
aden mcp install --platform <platform>
----

Supported `<platform>` values: `opencode`, `claude`, `cursor`, `codex`, `zed`, `windsurf`.

Useful flags:

* `--project <PATH>` — pin the project directory the server serves (defaults to CWD).
* `--binary <PATH>` — point at a specific `aden-mcp` binary if it is not on `PATH`.
* `--scope <SCOPE>` — `user` (global) or `project` (local). Default: user for Claude Code, project otherwise.
* `--dry-run` — print what would be written without touching any config.
* `--all` — install for every supported platform, not just detected ones.

Related: `aden mcp list` (platforms + install status), `aden mcp uninstall --platform <platform>`, `aden mcp serve` (HTTP endpoint for CI/agent integration).

=== Verify it works

1. Confirm the binary is reachable: `aden-mcp --version`.
2. Check the client config was written: `aden mcp list`.
3. *Fully restart your AI client* so it loads the new server.
4. In the client, confirm the `aden` tools appear (e.g. `grep`, `ask`, `asm`, `query`, `locate`). Ask it to `grep` a known string and confirm matches come back tagged with their enclosing symbol.

If the tools do not appear, see <<troubleshooting>>.

=== Argument conventions

* *Use `snake_case` argument names* (`dry_run`, `caller_of`, `show_context`). The server translates them to the CLI's `--kebab-case` flags.
* *Unknown arguments are rejected* at the schema boundary — a typo like `dept` for `depth` fails fast.
* *Booleans must be real JSON booleans* (`true`/`false`), not strings.
* *`locate` requires at least one of `symbol` or `caller_of`*.
* *Anchors, not bare names.* `asm`/`query` take a full `aden://…` anchor (or a module alias like `mod-<crate>`), not a bare symbol name. Use `grep`/`locate`/`list` to resolve the anchor, then feed it to `asm`/`query` — or use `understand` to skip the chain.

=== Security boundary

* *Path confinement.* Tools operate inside the served project directory; the `path`/`--project` argument defaults to it and the server does not reach outside (including `heal`'s watch target).
* *Error sanitization.* CLI errors are scrubbed of panic backtraces and absolute paths, and capped in length.
* *Timeout.* Long-running tools are bounded by a 120-second guard.
* *`watch` is terminal-only.* The continuous file-watch / live-reindex mode is not exposed over MCP — run `aden watch` in a terminal; use `gen`/`sync` for one-shot updates.

== How `aden ask` Works

`aden ask` is the primary interface for AI agents. It is not a chatbot wrapper around an LLM. It is a **context retrieval engine**.

Invocation:

[source,bash]
----
aden ask "How does the authentication flow work?"
----

What happens internally:

1. **Search**: The question is tokenized and searched against the in-memory inverted index built from all `.adoc` / `.aden` contracts.
2. **Anchor resolution**: The top-ranked document anchor becomes the starting node (or you pin it with `--from`).
3. **Intent classification**: The question is classified into one of nine intents (the per-intent code edges below; every intent additionally traverses the semantic edges IsA, RelatesTo, SimilarTo, AssociatedWith, Explains, and `Calls` is always included):
   - `Debug` --- "Why does X fail?" → depth 3, edges: Constrains, Documents, Calls, Invokes, Requires
   - `Usage` --- "How do I use X?" → depth 2, edges: Uses, Invokes, Requires, Documents
   - `Explain` --- "What does X do?" → depth 2, edges: Uses, Calls, Implements, Documents
   - `Refactor` --- "Refactor X" → depth 4, edges: Calls, Uses, Mutates, Supersedes, Amends
   - `Impact` --- "What depends on X?" → depth 3, edges: Uses, Calls, Constrains
   - `List` --- "list/show me all X" → depth 2, edges: Uses, Documents
   - `Compare` --- "compare X and Y" → depth 3, edges: Uses, Documents, Constrains
   - `Count` --- "how many X" → depth 1, edges: Documents, Uses
   - `General` --- fallback → depth 2, edges: Uses, Documents, Constrains
4. **Graph traversal**: A BFS walk collects neighbors along the selected edge types, stopping at `max_depth`. Each node's neighbors are expanded in deterministic edge-priority order (most load-bearing types such as `Calls` first), so the budget favors the most relevant context and the output is reproducible.
5. **Token budgeting**: Each collected document is estimated with a bytes/4 heuristic; documents are included until the cumulative total (inter-document separators counted) would exceed the budget, and an overflowing final document is truncated at a word boundary. `asm` treats `--budget` (default 8192) as a hard cap — output never exceeds it. `ask` instead *boosts* the budget by the match relevance by default (up to ~4x, capped at 32k), treating `--budget` (default 4096) as a base; pass `ask --strict` to make it an exact cap.
6. **Assembly**: Documents are concatenated with `\n\n---\n\n` separators. Output is stripped of AsciiDoc markup (anchors, refs, attribute lines, block delimiters) so every token carries signal.

== What to Do with the Output

Feed it directly into an LLM prompt. No preprocessing needed — the output is already token-dense:

[source]
----
You are an expert software engineering assistant.
The following context was retrieved from a knowledge graph.
Answer based ONLY on the provided context.
If the context does not contain enough information, say so explicitly.

---

[context from aden ask goes here]
----

This guarantees the agent reasons from real source structure rather than hallucinating APIs.

== When to Use `aden asm` Instead

`aden ask` is opinionated: it classifies intent and picks edges automatically. `aden asm` gives you full control.

Use `aden asm` when you already know the starting anchor and want exact edge types:

[source,bash]
----
aden asm --from mod-aden-graph --depth 3 --budget 8192 --edge-types "Uses,Calls"
----

This is useful for:
- Custom agent pipelines
- Debugging why `aden ask` returned too much or too little context
- Building reproducible prompts for regression tasks

== When to Use `aden query`

`aden query --from <anchor> --depth N` traverses the graph and emits JSON —
ideal both for sanity-checking structure before asking and for programmatic
consumption:

[source,bash]
----
# Reachable nodes from an anchor
aden query --from mod-aden-core --depth 2 . | jq '.[] | .anchor'

# Everything that references this anchor (backlinks)
aden query --backlinks mod-aden-core . | jq '.[] | .anchor'

# Transitive closure over dependency edges (blast radius)
aden query --impact mod-aden-core . | jq '.[] | .anchor'
----

== Finding Symbols with `aden locate` and `aden search`

`aden locate --symbol <name>` finds symbol definitions (functions, types, modules). Falls back to full-text search if graph search finds nothing.

[source,bash]
----
# Find a function definition
aden locate --symbol assemble .

# Find with limit
aden locate --symbol "Error" . --limit 5
----

`aden search <query>` performs full-text search across all contracts:

[source,bash]
----
aden search "authentication" . --limit 10
----

== Getting Command Help with `aden suggest`

Not sure which command to use? Ask `aden suggest`:

[source,bash]
----
aden suggest "find all tests in the project"
# Suggests: aden search "test" or aden locate "test"
----

| Task | Command |

== MCP Tools (for AI Platforms)

When using Aden via MCP (OpenCode, Claude Code, Cursor, etc.), the server exposes
its CLI as tools — one per `aden` subcommand. The surface is *tiered* so the
default tool list stays focused:

* *Core* — the read/query, validate, and build tools an agent reaches for
  constantly. Listed by default, ordered most-used first.
* *Extended* — setup / admin / niche tools. Hidden from the tool list to save
  context, but still callable by name. Set `ADEN_MCP_FULL=1` in the server
  environment to list them too.

A few of the most-used tools list their key arguments below; for the rest, run
`aden <tool> --help`.

NOTE: `watch` (and `heal --watch`) is a long-running, blocking process and is
*terminal-only* — it is not exposed over MCP at all. The MCP server times out any
blocking tool at 120s, so run `aden watch` from a shell for file-watching.

NOTE: Over MCP, the search tools (`grep`, `search`, `list`) return a structured
JSON envelope automatically — `{total, returned, truncated, ...}` — not the human
table or "... and N more" footer. The agent reads counts and truncation as data.
The anchor for `asm`/`query` is passed via `from` (there is no `--anchor` flag).

== Keeping the Graph Fresh

Stale context is worse than no context. Use this order in your agent loop:

1. Before starting work: `aden status .` (quick health check) or `aden check .` (validate integrity)
2. After writing code: `aden gen <path>` (index changed source)
3. Before committing: `aden ready .` (fast aden-only gates: gen + lint + check + heal drift + audit)
4. Before pushing to remote: `aden ci-check .` (full gate suite including external tools)
5. After large merges or file deletions: `aden sync .` (reconcile store — runs gen + check + heal with gc)

NOTE: Do NOT chain `aden gen` before `aden ready` or `aden ci-check` — both already run gen internally as their first step. Running gen twice wastes time and may produce inconsistent results.

If you are running as a persistent agent, use `aden watch` to auto-regenerate contracts on file changes.

== Understanding Drift Types

When `aden heal` runs, it detects these drift event types:

|===
|Drift Kind|Meaning|Auto-fixed by `--fix`?
|StaleHash|Source changed, contract hash stale|Legacy on-disk only (0.99); a store-resident StaleHash is skipped with a "run `aden gen`" hint
|SignatureMismatch|Symbol signature changed|Yes (0.90) — rewrites the signature in the store, not an on-disk stub
|MissingContract|Source symbol has no contract|Advisory: proposal points at the source and emits `aden gen <src> --auto .`; it does NOT materialize a stub (a stub has no `source_hash` and would self-drift as StaleHash)
|StaleMarkdown|Markdown's source files changed|Yes (0.80)
|MarkdownDrift|Markdown content drifted|No (confidence 0.75, below the 0.8 auto-fix threshold) — detect-only
|OrphanAnchor|Contract/anchor with no live source (deleted OR newly `.adenignore`-excluded)|No via `--fix`; removed via `--gc`
|BrokenReference|`<<anchor>>` points at a missing target|No (detect-only)
|DeadLink|`include::` path doesn't resolve|No (detect-only)
|MissingMarkdownTemplate|Markdown lacks its template|No (detect-only)
|===

NOTE: `--fix` only applies fixes with confidence ≥ 0.8.

NOTE: deleting a symbol or file no longer needs a manual step — `gen` prunes
removed symbols on re-index, and `aden heal . --gc` sweeps the store for
contracts whose source no longer exists.

Use `aden heal . --fix` for auto-fixing high-confidence issues.

== Token Economy Rules

Aden is designed with token scarcity in mind. Follow these rules:

- **Prefer `aden ask` over dumping the whole repo.** It stays within budget automatically.
- **Use `--from` to avoid search ambiguity.** One good anchor is worth ten vague keywords.
- **Lower `--budget` for focused tasks.** 2048 tokens is enough for most refactor questions.
- **Review the summary footer.** `aden ask` prints node count, bytes consumed, and budget status. If it says "OVER BUDGET", raise the limit or reduce depth.

== Security Notes for Agents

- Aden assumes contracts are build artifacts. Never commit `.aden/`.
- `aden init` generates `.adenignore` with security defaults. Do not remove entries that skip `*.env`, `secrets/`, or `target/`.
- Include directives are bounded to the project root. Path traversal outside the repo is rejected at parse time.

== LLM System Prompt

When an aden MCP tool is available, include this in your system context:

[source]
----
You have access to Aden, a knowledge graph compiler for codebases.

## Aden Tools Available:
- `ask(question)`: Ask natural language questions about the codebase
- `ask(question)`: Natural-language question — best first tool for exploration
- `search(query)`: Full-text search with semantic understanding, --semantics flag for graph edges
- `asm(from, depth)`: Assemble context from a starting anchor (passed as `from`)
- `query(anchor, depth)`: Get structured graph neighborhood as JSON
- `locate(symbol)`: Find symbol definitions and call sites, --show-context N for surrounding code
- `understand(symbol)`: One-shot comprehension — definition + backlinks + impact + context in one call; replaces locate + query --backlinks + query --impact + asm
- `list()`: List all available anchors, --semantics for semantic nodes
- `grep(pattern)`: Structure-aware search — every hit tagged with its enclosing symbol
- `heal()`: Check documentation health, --fix for auto-fix, --gc for orphan cleanup
- `status()`: Get health score and actionable orphan count
- `ready()`: Fast pre-commit gate — gen + lint + check + heal drift + audit (aden-only, no external tools)
- `sync()`: Reconcile store — gen + check + heal with gc; use after merges or file deletions, NOT as a pre-commit step
- `ci-check()`: Full gate suite including external tools (clippy, cargo audit, etc.); use before push
- `gen()`: Generate contracts, --auto for whole project, --quiet for summary only
- `check()`: Validate all references
- `lint()`: Lint source files; --dead-code for graph-based unreferenced symbol detection
- `test()`: Run tests
- `complete()`: report contracts that need completion (automatic LLM filling is not yet implemented)

## Best Practices:

1. START WITH `ask()` for exploratory questions
   - Good: "How does authentication work?"
   - Good: "What is the main entry point?"
   - Bad: "Show me everything" (too vague)

2. USE `search()` when you know specific terms
   - Good: `search("token budget")`
   - Good: `search("AdenGraph struct")`

3. USE `asm()` or `query()` when you have an anchor
   - Good: `asm("module-aden-core", depth=2)`
   - Good: `query("auth-module", depth=1)`

4. USE `locate()` for symbols
   - Good: `locate("main")`
   - Good: `locate("authenticate_user")`

5. CITE YOUR SOURCES
   - Always mention which documents informed your answer
   - Use the anchor names as citations

## Understanding Aden Output:

Aden returns **LLM-dense prose by default** — stripped of AsciiDoc markup noise:
- No `[[anchor]]` lines (anchors are in the header comment only)
- No `|===` table syntax (tables rendered as key: value pairs)
- No `:key: value` attribute lines
- No block delimiters (`----`, `====`, etc.)
- Headings converted to plain text

**Every token carries signal.**

If you need raw AsciiDoc (e.g. for an IDE renderer), opt in explicitly:

[source]
----
aden asm --from mod-aden-core --format aden .
----
----

== Common Patterns

=== Pattern 1: Understanding a New Codebase

[source]
----
1. ask("What is this project about?")
2. ask("What are the main components?")
3. list()  # See available anchors
4. asm("architecture", depth=2)  # Get architecture context
----

=== Pattern 2: Finding How Something Works

[source]
----
1. search("authentication")  # Find relevant docs
2. locate("authenticate")  # Find the function
3. asm("auth-function", depth=2)  # Get full context
----

=== Pattern 3: Making Changes Safely

[source]
----
1. locate("function_to_change")
2. query("function_to_change", depth=2)  # See what depends on it
3. ask("What breaks if I change X?")
4. check()  # Validate no broken refs
----

== Anti-Patterns

- **Don't** call `asm()` with depth=5 (wastes tokens)
- **Do** start with depth=2, go deeper if needed

- **Don't** use vague questions like "tell me about the code"
- **Do** ask specific questions like "what is the entry point?"

- **Don't** ignore citations in aden output
- **Do** reference specific documents in your answers

- **Don't** assume aden knows everything
- **Do** use `check()` to validate, `heal()` to find gaps

== Troubleshooting

=== `aden ask` returns "No relevant documents found"

Try more specific keywords from actual anchors. Run `aden search <keyword>` to see what anchors exist.

=== Output is too short

The graph parser currently stores document body content as raw text. If blocks are empty, it falls back to `raw_content`. If you see only titles, verify the `.adoc` files contain actual prose below the title.

=== DuplicateAnchor errors after `aden init`

Template files and instantiated files sometimes share anchors. Rename the instantiated file anchors (e.g., `[[agent-context]]` instead of `[[agent-context-template]]`) or delete the template files if they are not needed.
