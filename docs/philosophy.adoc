= Aden Philosophy

== The Core Thesis

The hard constraint in AI-assisted development is *context*, not model
intelligence. Dropped into a 100k-line codebase, an agent faces information
overload: it does not know which ten files matter, that changing
`Database::connect()` breaks `QueueWorker::drain()`, or what the system's shape
is. Aden exists to make the *structure of understanding* explicit,
machine-readable, and traversable — so the right context can be assembled on
demand instead of guessed at.

The name is the mission: *A Dense Referential Context Compiler*. Every token is
load-bearing, every edge is typed, every anchor resolves.

== What Aden Is — and Is Not

Aden is a **referential context compiler**. It compiles source, docs, notes, and
plans — in any language — into a traversable knowledge graph whose nodes are
documents and whose edges are typed semantic relationships.

It is *not*:

- a documentation generator (Rustdoc/Javadoc) — those render HTML to *read*;
  Aden produces context to *reason over*, for a human, an agent, or CI.
- a static analyzer (clippy/Semgrep) — it tracks semantic relationships and
  keeps them in sync as code evolves, rather than finding bugs in control flow.
- an IDE replacement — it is a substrate your IDE, agent, or pipeline queries to
  understand the system.

== Design Rationale

=== Why AsciiDoc

The native format is AsciiDoc because it is human-readable *and* fully
scriptable: a regular-enough grammar to parse deterministically, with anchors
(`[[name]]`), cross-references (`<<name>>`), attributes, and tables that map
directly onto graph nodes and edges. Plain text diffs cleanly in Git, so
contract changes are reviewable in a pull request like code, and `aden gen` can
regenerate contracts reproducibly from source.

=== Why a Graph

Software is a network, not a tree: modules `use` each other, functions `call`
each other, ADRs `constrain` decisions, tests `verify` behavior. A directory
tree cannot express those relationships; a directed, typed graph can. That is
what lets Aden answer questions `grep` cannot — what depends on this, what the
blast radius of a change is, what context an agent needs for a given file.

=== Why Token Density

Every token an LLM consumes costs budget and dilutes signal. `aden asm` performs
a budgeted graph traversal: from a starting anchor it walks edges and assembles
a prompt that fits a token budget while keeping the most load-bearing
relationships. The difference is surgically selecting context versus dumping a
codebase into a prompt.

=== Why Separate Generated Facts From Human Intent

A contract has two owners with different authority. The **generated** layer —
signatures, call edges, structure — is machine-owned: extracted from source, it
must track source exactly or the graph drifts into the staleness Aden exists to
prevent. The **intent** layer — "this must stay pure", a load-bearing invariant,
an agent's design note — is human/agent-owned and must never be silently
overwritten.

Aden keeps them apart by ownership. Generated content lives in the rebuildable
per-user store (`aden store path`; see <<adr-003>>), which `aden gen` overwrites
freely. Durable intent lives in sparse, git-tracked overlays authored with
`aden overlay <anchor>`. On every `gen`, a per-symbol three-way merge updates the
generated layer, preserves the overlay, and folds intent into the read graph so
`asm`/`ask`/`query` deliver both. When an annotated symbol changes, Aden emits a
one-time review notice (`.aden/proposals/`) — it *notifies*, it does not *block*.

== The Agent-First Mindset

Aden was designed for the autonomous agent. An agent does not need pretty HTML;
it needs five things, and Aden provides each:

. an accurate map of relationships — the graph
. a way to know when the map is stale — `heal`
. a way to assemble just-enough context for a task — `asm` / `ask`
. a way to verify work before committing — `check`
. a way to leave breadcrumbs about what changed — `session`

When a human reviews an agent's pull request, they read the contracts, run
`aden check`, and confirm the session log explains what changed and why.

== Security as a First-Class Concern

Because Aden serves automated agents that read files and run commands, security
is part of the design, not an afterthought:

- **Path traversal:** `include::[]` directives are canonicalized and bounded to
  the project root — an agent cannot inline `/etc/passwd`.
- **Safe execution:** tool discovery avoids cwd resolution to prevent binary
  planting; JSON deserialization is bounded and rejects unknown fields.
- **Sanitized identifiers:** proposal IDs are validated against an ASCII-safe
  whitelist before use as filenames.
- **No `unsafe`:** application/library code contains zero `unsafe` blocks (test + MCP startup env hacks only).

See <<security-model>> for the full threat model.
