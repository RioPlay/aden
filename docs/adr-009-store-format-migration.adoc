= ADR-009: Store Format Change Recovery (fjall 3 migration + freshness coupling)

== Context

PR #44 upgraded the storage engine from fjall 2.11 to fjall 3. fjall 3 writes a
different on-disk format than 2.11, and there is *no migration path*: opening a
store written by the old binary fails with a raw error and the command exits.

[source]
----
Error: Failed to open store at ~/.local/share/aden/projects/<hash>/store:
       IO error: FjallError: InvalidVersion(Some(V2))
----

This was found while testing the post-#44 release on a machine with a real
history of use: *every* existing store (~350 of them under
`~/.local/share/aden/projects/*/store`) is in the old V2 format, so a user's
first command after upgrading fails. The store is a rebuildable cache
(<<adr-003>>: "safe to delete, rebuilt from source"), so this should be a
recoverable cache-miss, not a fatal error.

Two defects compound here:

*Defect A — no graceful recovery on a format mismatch.* The conversion
`impl From<fjall::Error> for StoreError` collapses *every* fjall error into
`StoreError::Io(String)` (`crates/aden-store/src/fjall_store.rs`), so the
version mismatch is indistinguishable from a genuine I/O failure and nothing
downstream can react to it. `aden gen` opens the store via `Storage::new`
(`crates/aden-cli/src/commands/generate.rs`, `cmd_gen_inner`) and propagates the
error.

*Defect A2 — the obvious recovery is a silent-empty-graph trap.* Freshness is
tracked in `gen-cache.json` and `scan-cache.json` in the project directory,
*decoupled* from `store/`. So the natural fix for Defect A — delete `store/` and
re-run `aden gen` — produces a graph with no symbols:

[source]
----
$ rm -rf ~/.local/share/aden/projects/<hash>/store
$ aden gen .
Stored 0 contracts. Skipped 230 unchanged files.   # exit 0
$ aden status .
✅ Health: 100/100                                  # reports healthy
$ aden understand SomeSymbol .
No symbol found ...                                 # graph is empty
----

`cmd_gen_inner` trusts the per-file mtimes in `gen-cache.json` and skips every
file as "unchanged", even though the store it is writing into is empty. The read
path (`ensure_fresh`) already rebuilds when the store directory is *absent*
(`generate.rs`), but the explicit `gen` path has no such guard, and neither path
treats an *empty* store as a cache invalidation.

`status`/`doctor` reporting `100/100` on an empty graph is a secondary symptom
(health is computed from orphan ratios, which are vacuously perfect when there
are no nodes).

== Decision

Make a store-format change a *recoverable cache miss*, and couple freshness to
the store so recovery cannot silently no-op. Three parts.

=== 1. A typed, catchable version-mismatch error

Add a variant to `StoreError` (`crates/aden-store/src/lib.rs`):

[source,rust]
----
#[error("incompatible store format: {0}")]
IncompatibleVersion(String),
----

In `FjallStorage::new`, detect the fjall version-mismatch error and map it to
`IncompatibleVersion` instead of the generic `Io`. Preference order for
detection:

. Match fjall 3's typed error variant if it exposes one (preferred — stable).
. Fall back to sniffing the error's `Display`/`Debug` for the `InvalidVersion`
  marker, documented as brittle, *only* if (1) is not available.

This keeps every *other* fjall error on the `Io` path untouched, so the new
behavior is scoped to exactly the format-change case.

=== 2. Graceful rebuild on the write/create path

Only the *creation* path (`gen`/`heal`, which are about to rewrite the store
anyway) may auto-recover by wiping. When `FjallStorage::new` — or the gen
store-open in `cmd_gen_inner` — gets `IncompatibleVersion`:

. Print a one-line notice: `store format changed (engine upgrade) — rebuilding
  from source`.
. Remove the store directory contents.
. Recreate the store and proceed with a full gen.

*Guardrail (non-negotiable):* auto-wipe fires *only* on `IncompatibleVersion`,
never on `Io`/corruption/permission errors — those must still surface, because
silently deleting a store on an ambiguous error would mask real damage. The wipe
targets only the `store/` subdirectory, never the sibling caches or
`embeddings-cache.json` (those are handled in part 3).

*Pinned-store safety (added in implementation):* when `$ADEN_STORE` is set, the
store is a *shared* location that may hold several projects' data. The recovery
path must NOT auto-wipe it. In that case `cmd_gen_inner` surfaces an actionable
error ("`$ADEN_STORE` is pinned/shared — unset it or run `aden regen`") instead
of deleting shared state. This mirrors `regen`'s existing pinned-store caution.
The default per-project store is safe to wipe.

The *read* path also recovers, with no user action (added in implementation).
`ensure_fresh` (which every read calls) probes the store open; on
`IncompatibleVersion` it triggers the silent rebuild — so a read on an
incompatible store auto-recovers instead of degrading to empty results. Without
this, a post-upgrade read on an unchanged tree would skip the mtime-based
refresh, open the incompatible store, and return nothing. The probe is targeted
to the version-mismatch signal only (never a transient I/O error).

=== 3. Freshness follows the store

So an empty store can never be mistaken for "up to date": in `cmd_gen_inner`, a
store that does not exist (first gen, a manual `rm -rf store/`, a `regen` wipe,
or a just-recovered store) forces a full re-scan, ignoring the stale incremental
`gen-cache.json`. Without this, every file is skipped as "unchanged" against an
empty store and the rebuild silently produces nothing — the recovery-from-
deletion trap.

*Decision change from the proposal:* the originally-proposed `gen --rebuild`
flag was DROPPED. The existing `regen` command already provides a discoverable
clean rebuild (it wipes the whole per-user project dir — store + caches +
embeddings — and is inherently immune to the format hazard since it wipes
first). With the empty-store guard above, a plain `rm -rf <store> && aden gen`
also rebuilds correctly *and* preserves the expensive embeddings cache. A new
flag would only add overlapping surface (and an MCP-parity obligation) for a
capability that already exists, so it was not added.

Optionally (secondary, deferred): have the health score in `status`/`doctor`
report an empty store as unhealthy rather than `100/100`, so the trap is visible
if it ever recurs. (Tracked as a follow-up under the "trustworthy retrieval"
work, not this ADR.)

== Consequences

* Upgrading the storage engine (this time, and any future format change) becomes
  a transparent one-time rebuild instead of a hard failure — on BOTH the write
  (`gen`) and read (`grep`/`ask`/`understand`) paths, with zero user action.
* The store stays a pure rebuildable cache (preserves <<adr-003>>): correctness
  never depends on the on-disk format being forward/backward compatible.
* The implicit empty-store guard makes ad-hoc recovery (`rm -rf store/`) and
  `regen` both rebuild correctly; no new flag was needed.
* The auto-wipe is deliberately confined to the version-mismatch signal, never
  fires on a transient I/O error, and never wipes a pinned/shared `$ADEN_STORE`
  — so it cannot escalate an ambiguous error into data loss.
* A store from a *future* fjall (e.g. after an aden downgrade) reports the same
  `InvalidVersion` and is rebuilt from source by the older binary. Safe for a
  cache, but worth knowing.

=== Surface touched (all in the LSM/store path — gated)

* `crates/aden-store/src/lib.rs` — new `StoreError::IncompatibleVersion`.
* `crates/aden-store/src/fjall_store.rs` — `From<fjall::Error>` maps the typed
  `InvalidVersion` to `IncompatibleVersion`; every other error stays `Io`.
* `crates/aden-cli/src/commands/generate.rs` — `cmd_gen_inner` recovery +
  pinned-store guard + empty-store freshness guard; `recover_if_incompatible_store`
  helper; `ensure_fresh` read-path recovery probe.
* `crates/aden-cli/src/commands/heal.rs` — `cmd_heal_scan`/`cmd_heal_scan_since`
  call the recovery helper so heal also recovers (a blast-radius pass found heal
  opens the store directly and would otherwise silently find nothing). It uses the
  recovery-only helper, NOT `ensure_fresh`, so a normal heal still sees real drift.

=== Testing

* `aden-store` unit test: the typed mapping — `fjall::Error::InvalidVersion`
  maps to `IncompatibleVersion`, every other fjall error maps to `Io`. This is
  the linchpin; if a future fjall renames the variant, the test fails loudly.
* `aden-store` integration test: create a real store, corrupt its on-disk
  `version` marker, reopen — `Storage::new` surfaces `IncompatibleVersion`. This
  fabricates the signal portably (no committed V2 fixture, which fjall 3 cannot
  write) and is the same variant a genuine V2 store produces.
* Manual end-to-end against the real preserved V2 store: confirmed `gen`
  auto-rebuilds to a populated graph; a pure read auto-recovers; a manual
  `rm -rf store/ && gen` rebuilds (no silent-empty); embeddings cache survives;
  a healthy store still skips incrementally (no regression).

== Status

Accepted. Implemented in the store-format-recovery change. The originally
proposed `gen --rebuild` flag was dropped during implementation (see Decision
part 3). Defect B from the same testing pass (grep `PATH` not scoping the
search) shipped separately in PR #48.
