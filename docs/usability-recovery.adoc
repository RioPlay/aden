[[usability-recovery]]
= Source-read and worker recovery usability

== User-visible behavior

This increment fixes two demonstrated workflow failures:

* `aden read <file> --unlimited` now selects through EOF instead of silently
  keeping the default 200-line window. `--start-line` still chooses where to
  begin and an explicit `--end-line` remains authoritative. The 8192-byte
  excerpt and 16 MiB source-file caps remain; JSON provides a hash-pinned
  continuation when clipped. Human output gives clipping guidance on stderr.
* If a cached resident worker has already exited, the MCP director replaces it
  before sending the next request. That request can complete without making
  the caller repeat it. A transient startup failure uses serial execution for
  that call and retries worker startup on the next read, instead of permanently
  disabling the worker for that executable.

Confirmed protocol incompatibility still uses cached compatibility fallback.
Startup diagnostics are bounded and sanitized on server stderr. Malformed or
missing handshakes and ordinary startup crashes are not proof of incompatibility.
A valid PID is checked before accepting a different protocol as incompatible.

There is no automatic replay after a request may have been written. Timeouts,
cancellation and in-flight protocol errors retain the existing discard/error
behavior. Project and executable identity, environment restrictions, source
freshness and source-read path policy are unchanged. MCP `read` defaults and
its public schema are unchanged.

See <<ai-integration>> for direct source-read usage and <<mcp-read-sessions>>
for the resident worker boundary. The prepared symbol cache remains as described
in <<prepared-symbol-lookups>>.

== Installation and recovery

The verified pair is installed side by side in
`C:/Users/example/AppData/Local/Aden/versions/0.4.4-usability-2d925f0dfc1d/`.
Only the Codex Aden server's launch command was changed to the new `aden.exe`.
Parsed read-back preserved all other configuration values.

The default shell command previously resolved to the older `Aden/bin` directory.
Only that existing entry in the current user's PATH was replaced with the new
version directory. Other raw entries, order and the `REG_EXPAND_SZ` registry type
were preserved; machine PATH and old executable files were untouched. A process
with PATH reloaded from the machine/user registry resolved bare `aden` to the
verified CLI and read all 250 fixture lines with `--unlimited`. Evidence:
`.tmp/usability-next/shell-resolution.json`.

The installer sent a best-effort environment-change notification using the
link:https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-settingchange[documented Windows message].
Its short timeout applies per window, as specified for
link:https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessagetimeoutw[SendMessageTimeoutW].
Notification is not proof that an already-running host or terminal updated its
environment. Reopen the terminal and reconnect the MCP host to load the update.
No existing user server was forcibly restarted.

`activation.json` in the version directory records binary/configuration hashes,
the previous command, and PATH token/type/hash recovery metadata. It does not
retain the entire user PATH. The installed rollback helper restores the previous
PATH entry and MCP command while preserving unrelated settings:

[source,powershell]
----
python C:/Users/example/AppData/Local/Aden/versions/0.4.4-usability-2d925f0dfc1d/deploy_local.py --rollback C:/Users/example/AppData/Local/Aden/versions/0.4.4-usability-2d925f0dfc1d/activation.json
----

Installation review caught a rollback-ordering issue: an unexpected MCP command
could have caused a PATH rollback before the configuration guard failed. A
read-only configuration preflight now rejects that state before any mutation;
the final configuration guard remains. Fake-registry fixtures proved successful
activation/rollback, preservation of type/order and unrelated later additions,
already-restored behavior, and rejection of missing/duplicate/corrupt targets
and unexpected configuration. No real registry writes occurred in those fixtures.
Live activation then passed exact registry/configuration/binary read-back.

Other operating systems were not exercised. Malformed/incompatible handshake
classification has source review and related frame/process controls, but not a
separate process fixture for every handshake shape. No commit, PR, push or public
release was performed.
