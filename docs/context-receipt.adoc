[[context-receipt]]
= Context Receipt v1

A Context Receipt is protocol-neutral, machine-readable metadata about an Aden
result. It tells a human or agent what can be known about the context used to
produce the result without embedding source text, credentials, filesystem paths,
or arbitrary diagnostics.

== Wire format and migration

Receipt v1 is emitted as a nested `context_receipt` object in structured CLI
read results and is preserved verbatim by the MCP CLI bridge:

[source,json]
----
{
  "matches": [],
  "freshness": "current",
  "index_stale": false,
  "context_receipt": {
    "schema_version": 1,
    "freshness": "current",
    "graph_revision": "7cc7e6af741f2658",
    "observed_source_fingerprint": "df66a930273e405b",
    "refresh_cause": "none"
  }
}
----

The existing top-level `freshness`, `index_stale`, `stale_hint`, and `items`
fields remain available during the compatibility window. Consumers should begin
reading `context_receipt`, ignore unknown additive fields, and call
`validate_supported` to reject an unknown required schema version rather than
guessing its meaning. This is an additive
receipt-v1 migration, not a replacement for the legacy fields.

If a legacy object already owns the top-level `context_receipt` key, Aden
preserves that object rather than overwriting or wrapping it. That exceptional
legacy shape does not receive a v1 receipt until its producer migrates the key.

== Schema v1

`schema_version` is required. `freshness` is optional and mirrors Aden's legacy
freshness label. Current structured reads also include additive revision proof:
`graph_revision` identifies the published graph snapshot,
`observed_source_fingerprint` identifies the source tree seen by the read, and
`refresh_cause` records why a refresh was or was not attempted. Consumers must
still tolerate a minimal version-only receipt when a strict transport budget is
too small for optional metadata.

Receipt v1 intentionally defines no coverage, budget, retrieval, outcome, or
warning fields; their owning packets add them only after their semantics are
settled.

Receipt producers must not include
source text, query text, credentials, tokens, arbitrary diagnostic messages, or
filesystem paths in receipt metadata.

== Compatibility

The Context Receipt has an independent schema version. Additive optional fields
are compatible; removing, renaming, or changing a required field's meaning is a
receipt-schema major change. See <<compatibility>> for the full policy.
