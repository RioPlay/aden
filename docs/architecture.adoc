[[architecture]]
= Aden Architecture

== The Big Picture

Aden is a **referential context compiler** — it transforms codebases into traversable knowledge graphs. The goal is making the *structure of understanding* explicit, machine-readable, and queryable by both humans and AI agents.

[mermaid, aden-pipeline, svg]
----
flowchart TD
    A[Source Code] --> B[aden-parse]
    B --> C[aden-graph]
    C --> D[(Per-user store<br/>fjall)]
    D --> E[Knowledge Graph]
    E --> F[aden ask / asm]
    F --> G[Context for AI]
----

== Core Concepts

=== The Graph

Every document, function, module, and decision becomes a **node**. Every relationship — imports, calls, constraints, justifications — becomes a **typed edge**.

[source]
----
[[auth-module]]
= auth module

== Functions

* login() -- calls --> validate()
* validate() -- uses --> crypto()
* logout() -- calls --> session::clear()
----

Typed edges enforce referential integrity. Open strings are rejected.

=== The Contract

A contract is an AsciiDoc (`.adoc`) or Aden (`.aden`) file that describes a piece of the system. Contracts are **deterministically generated** from source code — the same source always produces the same contract.

[source]
----
[[module-aden-core]]
= module::aden-core

|===
|Type |Kind |Description
|Document |struct |Root node in the graph
|Block |enum |Content block types
|===
----

=== Region Semantics

Contracts support regions that determine how content is handled during regeneration:

|===
|Region |Purpose |Preserved on Regen?

|[generated] |Auto-extracted from source |No — overwritten

|[human] |Architectural notes, decisions |Yes

|[agent] |AI agent observations |Yes

|[security] |Security requirements |Yes

|[constitution] |Governance directives |Yes

|[override] |CI override authority |Yes
|===

=== Token Budgeting

AI agents have finite context windows. Aden budgets tokens by:

1. **BFS traversal** — walk the graph from a starting node, expanding each
   node's neighbours in deterministic priority order (most structurally
   load-bearing edge types first: `Calls`, then `Uses`, containment, …) so the
   budget is spent on the most relevant context and the output is reproducible
2. **Depth limiting** — stop at depth N (default: 3)
3. **Token estimation** — ~4-bytes-per-token heuristic (byte length ÷ 4)
4. **Assembly** — concatenate documents until the budget is reached. The budget
   is a hard cap: inter-document separators are counted, and a final document
   that would overflow is truncated at a word boundary rather than pushing the
   assembled output past the budget

=== 1. Parse (aden-parse)

Extracts symbols, signatures, and relationships from source code using tree-sitter.

|===
|Language |Depth |Analysis

|Rust |Deep |Full AST, trait bounds, lifetimes

|Python |Deep |Import-aware, decorators

|Go |Deep |Full AST, interfaces

|TypeScript/JS |Deep |Full AST, generics

|305+ others |Shallow |Generic AST fallback
|===

Discovery is **language-agnostic**: `aden gen --auto` walks the whole project and
keeps every file whose extension a parser can handle (the canonical set is
`aden_parse::supported_extensions()`), honoring `.adenignore`. It does *not* gate
on the build manifest, so a polyglot repo — or a Rust repo with Python scripts and
Markdown docs — is fully covered rather than reduced to a single language.

Grammars are compiled into the binary at build time via `TSLP_LANGUAGES` (set in
`.cargo/config.toml`); the language pack would otherwise download them at runtime,
which breaks offline and air-gapped use. See CONTRIBUTING.md.

=== 2. Graph Build (aden-graph)

Builds a directed graph (`DiGraph`) from all contracts + documentation + <<adr-001>> + <<project-context>>.

- Nodes: anchors (`[[name]]`)
- Edges: typed relationships (`Uses`, `Calls`, `Constrains`, `Documents`, etc.)
- Validation: cycle detection, orphan detection, reference resolution

=== 3. Validate (aden check)

Ensures referential integrity:

- Every `<<anchor>>` resolves to a real `[[anchor]]`
- No duplicate anchors
- No include cycles
- Source hash integrity

=== 4. Assemble (aden-asm / aden-ask)

Given a starting anchor and token budget:

1. BFS traversal from the anchor, expanding each node's neighbours in
   deterministic edge-priority order (e.g. `Calls` before `Documents`)
2. Collect documents along selected edge types
3. Estimate token count per document (and per separator)
4. Stop when the budget is reached; a final overflowing document is truncated at
   a word boundary so the assembled output never exceeds the budget
5. Concatenate (LLM-dense `---` separators by default; `<<<` in raw mode)

=== 5. Persist (aden-store)

`aden gen` is **store-first**: it writes the compiled graph only to the per-user,
per-project store (`aden store path` prints its location, e.g.
`~/.local/share/aden/projects/<key>/store`), a fjall LSM-tree keyed store with
postcard-serialized values. Per <<adr-003>> the store lives *outside* the working
tree and is never written into it. It does not emit `.adoc` contract files into
the project tree on any run.

The **source of truth** is the source code itself; the per-user store is the
**durable, rebuildable artifact** derived from it. If the store is missing,
stale, or deleted, it is rebuilt deterministically from the source — the same
source always produces the same store. An in-tree `.aden/store` is only a
legacy/back-compat read path: older stores there are still read (with a
deprecation notice) and migrated, but fresh `gen` never writes there.

== What happens when you run `aden ask`

A read command like `aden ask "How does auth work?"` runs end to end as:

1. **Auto-reindex** — any source file changed since the last run is re-parsed
   and the graph updated, so reads are always against a fresh graph (no manual
   `aden gen` required).
2. **Store lookup / rehydrate** — the compiled graph is loaded from the per-user
   store (fjall + postcard); if absent it is rebuilt from source.
3. **Search (aden-index)** — the question is matched to find the best
   entry-point anchors. BM25 by default; when the `dense` feature is built and a
   local model is present, this is a hybrid search (BM25 + dense embeddings fused
   via Reciprocal Rank Fusion).
4. **Assemble (aden-asm)** — a BFS traversal walks outward from those anchors
   along selected edge types, estimating tokens per document with the
   bytes ÷ 4 heuristic. `ask` boosts its base `--budget` (default 4096) by the
   match relevance by default — up to ~4x, capped at 32k — so a strong match
   gets more context; pass `ask --strict` for an exact cap.
5. **Result** — the selected documents are concatenated into a single assembled
   prompt context.

== Key Features

=== Self-Healing Contracts

When source code changes, contracts become stale. `aden heal` detects drift:

|===
|Event |Meaning |Fix

|StaleHash |Source changed, contract not regenerated |`aden heal --fix`

|MissingContract |No contract for source file |`aden gen`

|SignatureMismatch |Function signature changed |`aden heal --fix`

|OrphanAnchor |Contract has no incoming edges |Add `<<ref>>` or delete
|===

=== Three-Way Merge

The three-way merge engine lives in `aden-core` (`ContractState` /
`MergeProposal`). For each symbol it reconciles:

- **ground**: freshly parsed AST (`from_document` of the new parse)
- **base**: the generated document currently in the store (last `gen`)
- **working**: `base` plus the symbol's intent overlay (`[human]`/`[agent]`)

It is wired into `gen` (`reconcile_anchor`): the generated layer always updates
the store (so it never drifts from source), while durable overlay intent —
stored sparsely in git-tracked `.aden/overlays/<anchor>.adoc` — is preserved and
folded into the read graph so `asm`/`ask`/`query` surface it. When a symbol that
carries an overlay has its generated content change, `gen` writes a one-time
*review notice* to `.aden/proposals/` (notify, not block). `gen --propose` is a
dry-run; `gen --force-regen` skips the gate. Author overlays with
`aden overlay <anchor>`.

The engine produces a per-block `MergeAction`:

- `UpdateGenerated` — overwrite with new AST
- `PreserveHuman` — keep human blocks intact
- `Conflict` — cannot auto-merge, needs review
- `InsertGenerated` — new symbols detected
- `DeleteGenerated` — symbols removed from source

=== Constitutional Governance

The `[constitution]` block declares governance rules:

[source]
----
[constitution]
.agents = [claude, cursor]
.precedence = ai-overrides

[role=security]
===
The security agent has final authority on any code
touching authentication or authorization.
===
----

`aden check` resolves conflicts using stated precedence.

=== Hybrid Retrieval

Retrieval is BM25 by default. With the optional `dense` cargo feature (off by
default), `search` and `ask` *also* run local dense embeddings and fuse them with
BM25 via Reciprocal Rank Fusion (RRF; Cormack, Clarke & Buettcher, SIGIR 2009,
`RRF_K=60`). Embeddings use a pure-Rust `tract` ONNX runtime with
BAAI/bge-small-en-v1.5 (384-dim, CLS-pooled, L2-normalized). The whole path is
fully offline and deterministic, and it degrades cleanly to pure BM25 when the
feature is off or the model is absent.

The model is **fetch-on-demand** (not bundled): run
`scripts/fetch-bge-model.sh` to download it (~127 MB fp32) into
`~/.cache/aden-models`.

|===
|Component |Detail

|Lexical |BM25 over the inverted index
|Dense |bge-small-en-v1.5 via `tract` ONNX (384-dim, CLS-pooled, L2-normalized)
|Fusion |Reciprocal Rank Fusion (`RRF_K=60`)
|Feature flag |`dense` (off by default)
|Model |Fetched via `scripts/fetch-bge-model.sh` into `~/.cache/aden-models`
|===

Code: `crates/aden-index/src/lib.rs` (`rrf_fuse`, `hybrid_query`,
`dense_query`, `EmbeddingProvider`, `RRF_K`) and
`crates/aden-index/src/dense.rs` (`TractEmbedder`).

=== Community Detection & Blast Radius

`aden communities` clusters the graph into functional groups using deterministic
multi-level Louvain modularity (`crates/aden-graph/src/community.rs`). When
`ask` falls back to a thin stub, it now broadens to the enclosing functional
*community* rather than the module/project root.

`aden impact-diff` reports the blast radius of a git diff by reusing the impact
traversal (`crates/aden-cli/src/commands/impact_diff.rs`), so you can see what a
set of changes reaches downstream.

== Security Posture

- The knowledge-graph store is a rebuildable build artifact that lives outside the working tree (per-user, per-project) — see <<adr-003>>; legacy in-tree `.aden/store`/cache paths are auto-ignored in `.gitignore`, while durable intent under `.aden/` (overlays, constitution, hooks) is git-tracked
- Include directives bounded to project root — no path traversal
- No `unsafe` blocks in application code
- AGPL-3.0-or-later license prevents cloud capture without sharing modifications

== Project Context & Crate Map

NOTE: This section is the canonical shared memory for agent sessions working on Aden. Reference it at the top of agent prompts.

=== Language Defaults

- Rust Edition 2021/2024, latest stable.
- `thiserror` for all error enums; `serde` for all data interchange.
- Prefer `std::collections::HashMap` over `BTreeMap` unless order is required.
- All public APIs `#[derive(Debug)]`; all public API items have doc comments.

=== Project Glossary

Document:: The atomic node in the Aden knowledge graph. Has an anchor, node type, attributes, and blocks.
Edge:: Typed relationship between two Documents. Enforced by `aden-graph`.
Contract:: A table block within a Document describing an API surface or behavioral guarantee.
Block:: A content unit within a Document: table, paragraph, listing, admonition, or description list.
Symbol:: A named entity extracted from source code (function, type, trait, module).
Anchor:: A globally unique AsciiDoc identifier matching `^[a-z0-9_-]+$`.
Emitter:: The `aden-emit` crate that serializes `Document` structs into `.adoc` / `.aden` text.
Extraction:: Parsing source (Rust, Python, Go, TypeScript, Java, 300+ via tree-sitter) into a `Vec<Document>`.
ContractRegion:: Semantic region of a contract (`Generated`, `Human`, `Agent`, `Security`, `Contract`, `Constitution`, `Override`, `Proposed`). Determines merge behavior.
ContractState:: Three-way merge state (`ground`/`base`/`working`) for incremental contract generation.
Constitution:: A `[constitution]` block of precedence-ranked policy directives — the highest authority in the contract hierarchy.
Directive:: A policy rule (`Forbid`, `Warn`, `Suggest`, `Allow`) extracted from `[security]` or `[constitution]` blocks.
Override:: A `[override]` block that bypasses a directive with `:justification:` and `:reviewer:`.
Staging:: Write-only audit trail in `.aden/staging/` for agent proposals before promotion.

=== Agent Conventions

. Every `.adoc` file declares an anchor immediately before the title.
. Every table has a header row.
. Use `agent-note::` blocks for temporal annotations and uncertainty.
. Use `ifdef::agent[]` to hide human prose from AI context.
. Never use YAML frontmatter; use AsciiDoc attributes (`:key: value`).
. Resolve every `<<reference>>` to an existing `[[anchor]]`.

[[experimental-crates]]
== Experimental and Standalone Crates

Tracks crates in the workspace that are not fully integrated into core functionality. Status: `core` (fully integrated), `experimental` (implemented, not integrated), `standalone` (separate tool/binding).

=== Experimental Crates (Not Integrated)

None at present. The previously-tracked experimental crates (`aden-api`,
`aden-attest`, `aden-simulate`, `aden-telemetry`) were **removed** on 2026-06-03:
they had zero workspace dependents, were not wired into any binary, and existed
only as roadmap scaffolding (Phase 4-6). Their roadmap intent is still recorded
in the "Phase 1-6 Crate Map (Planned)" table above; the code can be reconstructed
from git history if/when those phases are picked up.

=== Standalone Crates (Separate Distribution)

**aden-lsp** — `crates/aden-lsp/` (~8KB), STANDALONE. Language Server Protocol implementation for IDE integration, distributed as a separate `aden-lsp` binary. Open decision: keep in workspace for convenience, move to an external repo for cleaner separation, or deprecate in favor of MCP-based IDE integration.

=== Core Crates (Fully Integrated)

`aden-core` (schema/types), `aden-parse` (language parsers), `aden-emit` (contract emission), `aden-graph` (knowledge graph, community detection), `aden-index` (BM25 + optional dense hybrid (RRF) search), `aden-asm` (context assembly), `aden-cli` (main binary), `aden-mcp` (MCP server), `aden-heal` (self-healing), `aden-propose` (patch generation, used by heal), `aden-policy` (constitutional directives), `aden-store` (fjall LSM-tree per-user store, <<adr-003>>), `aden-diagnose` (deterministic diagnostic scanner, backs `aden diagnose`), `aden-paths` (per-user, per-project path resolution and project identity, <<adr-003>>).

NOTE: `aden-mcp` is integrated but unusual — it has no `aden-*` crate
dependencies. It shells out to the `aden` binary as a sibling process
(`resolve_aden_binary` + `tokio::process::Command`) rather than linking the
core crates directly.

=== Governance

New crates should start as: (1) features in existing crates (preferred), (2) experimental crates with a clear integration path, or (3) standalone crates only with strong justification. Experimental crates older than 12 months without integration plans should be archived to separate repos or removed.

The cleanup of the four removed crates is complete (documented, decided **remove** as declaration-only roadmap scaffolding, and removed on 2026-06-03).
