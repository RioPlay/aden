= From Opaque Code to Understandable Context in Minutes

== What Problem Does Aden Solve?

You have a codebase. Maybe it is 5,000 lines, maybe it is 500,000. Either way, nobody understands all of it. When you need to refactor a core function, you do not know what breaks. When a new engineer joins, they spend days reading files before they can ship. When you ask an AI agent to help, it hallucinates because it lacks context.

Aden solves this by turning your project into a **traversable knowledge graph**.

Every document, function, module, and decision becomes a node. Every relationship --- imports, calls, constraints, justifications --- becomes a typed edge. You can then ask precise questions and get precisely the context you need, automatically assembled within a token budget.

== What Aden Actually Does (No Jargon)

1. **Parses your source code** into structured contracts (`.adoc` / `.aden` files) using tree-sitter.
2. **Builds a directed graph** from all those contracts plus your manually written docs, plans, and ADRs.
3. **Validates** that every cross-reference (`<<ref>>`) resolves to a real anchor (`[[anchor]]`).
4. **Answers questions** via `aden ask` --- it searches the graph, classifies your intent, and assembles a context prompt from the relevant documents.
5. **Detects drift** via `aden heal` --- when code changes, it flags stale contracts and proposes updates.

It is like `grep` that understands semantics, combined with a documentation tool that never rots.

== Why AsciiDoc? Scriptable, Repeatable, Machine-Navigable

Aden uses AsciiDoc because it is the only markup format that is simultaneously human-readable and fully scriptable:

- **Deterministic generation**: `aden gen src/lib.rs` produces the exact same contract every time for the same source. Contracts are build artifacts, not hand-typed prose.
- **Parameter substitution**: Templates declare `:key: value` attributes and use `include::[]` composition. The `aden workflow` command instantiates templates with real values, making onboarding documents and runbooks repeatable across projects.
- **Testable references**: Every `<<anchor>>` is validated by `aden check`. Broken links are CI failures, not stale bookmarks.
- **Version-control friendly**: Because everything is plain text, diffs show semantic changes (new fields, renamed functions) rather than binary blob churn.
- **Graph-native**: AsciiDoc's `[[anchor]]` and `<<reference>>` syntax maps directly to graph nodes and edges. No preprocessor magic required.

In short: Markdown is for humans reading. AsciiDoc is for machines *and* humans reasoning.

== Quick Start (Zero to Working in 5 Minutes)

=== Install

[source,bash]
----
# Via Cargo (from this repository)
cargo install --path crates/aden-cli

# Or from GitHub
cargo install --git https://github.com/RioPlay/aden
----

=== Initialize Your First Project

[source,bash]
----
cd your-project
aden init        # Scaffolds .agent/ templates and .adenignore
aden gen src/ --auto  # Generates .adoc contracts from all source files
aden check .          # Validates every reference resolves
aden ask "How does the error handling work?"
----

After `aden gen`, look in `./contracts/` (auto-ignored by Git) for the generated contracts. After `aden check`, you know your graph is internally consistent.

=== What the Output Looks Like

`aden ask` resolves your question to the most relevant document, classifies your intent (`Explain`, `Usage`, `Refactor`, `Impact`, `Debug`, or `General`), and performs a BFS traversal to assemble related context within a token budget. The output is raw AsciiDoc you can feed directly to an LLM.

Example:

[source]
----
$ aden ask --from mod-aden-core "What is the Document type?"
// Aden Ask: 'What is the Document type?' → [[mod-aden-core]]
// Strategy: Explain | Depth: 2 | Edges: "Uses, Calls, Implements, Documents"

== Command Reference (What You Actually Run)

|===
|Command |When to Use It |Example

|`aden init` |First time in any repo |`aden init .`
|`aden gen <path>` |After modifying source files |`aden gen src/lib.rs`, `aden gen src/ --auto`
|`aden gen --merge` |Preserve human blocks, update generated only |`aden gen src/lib.rs --merge`
|`aden gen --propose` |Dry-run merge preview |`aden gen src/lib.rs --propose`
|`aden check <path>` |Before every commit |`aden check .`
|`aden ask <question>` |You need context fast |`aden ask "What depends on auth_module?"`
|`aden ask --from <anchor>` |Pin the starting point |`aden ask --from auth_module "What breaks if I rename this?"`
|`aden query --from <anchor> --depth N --format table` |Visualize dependencies |`aden query --from mod-aden-core --depth 3 --format table`
|`aden asm --from <anchor>` |Build a custom LLM prompt |`aden asm --from plan-phase0 --depth 2 --budget 4096`
|`aden query --backlinks <anchor>` |Find everything that references X |`aden query --backlinks mod-aden-core .`
|`aden query --impact <anchor>` |See blast radius |`aden query --impact Database .`
|`aden search <query>` |Full-text search |`aden search "token budget" .`
|`aden heal <path>` |Detect stale docs |`aden heal .`
|`aden ci-check <path>` |Run all gates at once |`aden ci-check .`
|`aden watch <path>` |Auto-regenerate on save |`aden watch src/`
|===

== Architecture at a Glance

Aden is a Cargo workspace. Each crate has a single responsibility.

|===
|Crate |What It Does

|`aden-core` |Schema: `Document`, `Block`, `Edge`, `Symbol`, etc.
|`aden-parse` |Language routers and AST extraction (Rust, Python, Go, TS/JS, and 305+ generic)
|`aden-emit` |Deterministic AsciiDoc emitter
|`aden-graph` |Graph engine: `DiGraph`, cycle detection, typed edges, integrity checks
|`aden-asm` |Context assembler: BFS traversal + token budgeting
|`aden-index` |In-memory inverted index for full-text search
|`aden-heal` |Drift detection and health scoring
|`aden-propose` |Patch generation for stale contracts
|`aden-mcp` |MCP server (Claude, Cursor, Zed, Windsurf)
|`aden-lsp` |LSP for `.adoc` / `.aden` files
|`aden-policy` |Constitutional policy engine: directives, precedence, conflict resolution
|`aden-py` |PyO3 Python bindings
|`aden-cli` |The `aden` binary with all commands
|===

== Security Posture

- `contracts/` and `.aden/` are build artifacts containing source paths. They are auto-added to `.gitignore` by `aden init`.
- Include directives (`include::[]`) are canonicalized and bounded to the project directory.
- No `unsafe` blocks in application code.
- AGPL-3.0-or-later license prevents cloud capture without sharing modifications.
