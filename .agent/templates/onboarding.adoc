[[onboarding]]
= Agent Onboarding Protocol

[TIP]
====
This document has **two paths**:

* **Path A** — You are starting a *new project from scratch*.
* **Path B** — You are joining an *existing codebase*.

Pick the one that applies. Do not mix them.
====

== Path A: Starting a New Project

Use this when there is no code yet, only an idea.

=== Step 1: Validate the Idea

Before touching code:

. Write xref:kickoff.adoc[]. Fill every section. If you cannot, the idea is not ready.
. Do not write code until the kickoff is complete.
. Kickoff defines success criteria. Without them, you cannot know when you are done.

=== Step 2: Design Before Building

. Write xref:design.adoc[] for the core architecture.
. Write xref:adr-{number}.adoc[] for every non-obvious decision.
. No code without an accepted ADR. No ADR without a kickoff.

=== Step 3: Specify What You Will Build

. Write xref:spec.adoc[] with acceptance criteria.
. Break the spec into xref:task.adoc[] entries.
. Every task must trace back to a spec criterion.

=== Step 4: Build with Checks

. Write code.
. Generate contracts: `aden gen <file>`
. Run tests.
. Run `aden check .`
. Run `aden ci-check .`
. Only then commit.

=== Step 5: Publish Runbook

Before shipping:

. Write xref:runbook.adoc[] for operations.
. Write monitoring checks.
. Define incident severity.
. Write xref:retrospective.adoc[] *template* for when things go wrong.

---

== Path B: Joining an Existing Project

Use this when the project already has code and contracts.

=== Pre-Flight Checklist

. Read xref:context.adoc[.agent/context.adoc] — shared memory
. Read xref:aden-guide.adoc[.agent/aden-guide.adoc] — canonical command reference
. Read xref:constraints.adoc[.agent/constraints.adoc] — mandatory negative rules (especially the Security & Subprocess sections)
. Read xref:session.adoc[.agent/session.adoc] — who is active right now
. Read xref:glossary.adoc[.agent/glossary.adoc] — terminology
. Read xref:style-guide.adoc[.agent/style-guide.adoc] — AsciiDoc formatting rules (no ASCII art)
. Read xref:security-audit.adoc[latest security audit] — what has been fixed and what patterns to avoid

== Phase 1: Assess Baseline Health (Before Code)

[source,bash]
----
aden check .                # All refs resolve? Health = 1.0?
aden doctor .               # Environment OK? No leaks detected?
aden heal --scan . --since HEAD~1
# If a security audit exists, verify no new HIGH-severity findings appear:
cat .agent/security_audit.adoc | grep -E "^\| High\s+\|" | head -1
----

[IMPORTANT]
====
If `aden check` returns errors, STOP.
Ask for human clarification or fix drift first.
====

== Phase 2: Lock Your Session

Mandatory atomic protocol: read → append → write → verify.

[source,bash]
----
# 1. Read session.adoc into memory
cat .agent/session.adoc

# 2. Append your entry (use ISO-8601 timestamp, UTC)
# Example:
# |2026-05-23T14:30:00Z |agent-7 |Refactor parser |src/parser/error.ext
# |in_progress |High

# 3. Overwrite session.adoc atomically
# 4. Re-read to confirm your entry exists
----

=== Entry Format (Strict)

[source,asciidoc]
----
|Timestamp |Agent |Task |Files |Status |Confidence
|===
----

Confidence levels:
* **High** (>0.9)
* **Medium** (0.7–0.9)
* **Low** (<0.7) — include a `blocker:` field explaining why

== Phase 3: Impact Analysis (Before Editing)

Before modifying any existing symbol:

[source,bash]
----
aden ask --from <symbol_name> "What depends on this and what breaks if I change it?"
aden graph --depth 2 <symbol_name>
aden locate --caller-of <symbol_name>
----

If over 10 backlinks exist, include `aden asm --from <symbol_name>` in your analysis.

== Phase 4: Implement + Generate

. Write code.
. Immediately generate its contract: `aden gen <file>`.
. Review the generated contract — does it accurately describe your change?
. If you changed a public API, update or create the module-level contract too.

=== Contract Quality Checklist

[circle]
- Does the contract have a `[[unique-anchor]]`?
- Is the Description paragraph non-empty and accurate?
- Are parameters current (match source signature)?
- Did you add an xref:style-guide.adoc#admonitions[admonition block] if behavior is uncertain?

== Phase 5: Validation

[source,bash]
----
<your-test-command>         # All tests pass (e.g. cargo test, pytest, go test)
aden check .
aden heal --scan .
aden ci-check .
----

If any step fails, do not declare completion. Fix and re-run.

== Phase 6: Close Session

. Update your entry in xref:session.adoc[.agent/session.adoc]:
** Change `Status` to `completed` or `cancelled`
** Add `Result:` field summarizing outcome
. Run `aden check .` one final time.
. If contracts changed, they are in `contracts/` — do NOT stage them.

== Emergency Procedures

[cols="1,2"]
|===
|Situation |Immediate Action

|Circular include detected by `aden check`
|Run `aden graph` to find cycle. Remove redundant include.

|Broken `<<refs>>` after rename
|Use `aden search "old_name"` to find all references, update them.

|`aden heal` shows StaleHash on your file
|You edited code without regenerating contract. Run `aden gen <file>`.

|Another agent modified a file you're editing (session conflict)
|Stop. Rebase your mental model: read their contract, resolve manually.

|Drift score drops below 1.0 after your changes
|Your code and contracts are out of sync. Review `aden heal --scan`.

|Token budget exceeded during reasoning
|Subdivide: ask smaller scoped questions. Use `aden locate` for precision.

|Low confidence (<0.7) on implementation
|Add xref:style-guide.adoc#admonitions[WARNING admonition] explaining risk. Do NOT auto-apply.

|===

[sidebar]
.Why Contracts Must Stay Private
****
A malicious actor who can modify or inject contracts can silently redirect every downstream developer toward insecure patterns.
Contracts are part of the software supply chain.
Never commit `contracts/` or `.aden/`.
****
